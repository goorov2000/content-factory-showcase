## 1. Что это за проект

**🎓 Сеньор:** Content Factory — data-driven пайплайн генерации контента для
Instagram/TikTok бренда одежды JE LA PECHE. Трёхслойная архитектура: n8n (self-hosted,
runtime-слой) скрейпит через Apify-акторов вирусные видео и метрики в Google Sheets;
интеллектуальный слой на агентах Claude Code (промпты в git, оркестрация через CLI
`python -m cf` и локальный FastAPI-дашборд) выполняет классификацию, статистический
анализ, вывод «формул» успешного контента и генерацию креативных брифов; оператор —
human-in-the-loop на всех решениях, меняющих промпты и утверждающих формулы. Обратная
связь замыкается через performance-метрики, еженедельный eval и evidence-backed
proposals на изменение промптов. (Решение 2026-07-22: система переезжает на
собственный VPS, n8n выводится после приёмки — см. docs/BUSINESS-CONTEXT.md.)

**🐣 Новичок:** это конвейер, который помогает одному человеку вести модный бренд в
соцсетях так, как будто у него целый отдел аналитиков и сценаристов. Роботы каждый
день собирают чужие залетевшие ролики про мужскую моду, машина считает, какие приёмы
реально работают (а не «кажется, что работают»), выводит из них «рецепты» (формулы),
по рецептам пишет сценарии роликов (брифы), а человек только нажимает «одобрить» или
«отклонить» и снимает по готовому сценарию. После публикации система смотрит на
просмотры и лайки и сама учится: какие рецепты живые, а какие пора выкинуть.

**Цель:** ~70 брифов в неделю на поток при одном операторе.

**Сёстры-репозитории:**
- `CF` (этот) — весь код и знания фабрики;
- `CF DS` — дизайн-система JE LA PECHE (DESIGN.md, шрифты Aeroport, логотипы) — по ней
  оформлен дашборд, см. [раздел 12](#12-дизайн-система-cf-ds).

## 2. Большая картина: цикл фабрики

```
   ┌──────────── СБОР (n8n, каждый день) ────────────┐
   │  TikTok/Instagram → Apify → Ingestion Gate →    │
   │  Google Sheets: CF Raw TikTok / CF Raw Instagram│
   └────────────────────────┬────────────────────────┘
                            ▼
   ┌────────── ИНТЕЛЛЕКТ (Claude Code агенты) ───────┐
   │ классификация ниш → профиль батча → анализ      │
   │ (winners/losers) → ПАТТЕРНЫ → ФОРМУЛЫ (proposed)│
   └────────────────────────┬────────────────────────┘
                            ▼
        оператор на дашборде: формула approved?
                            ▼
   ┌──────────── ПРОИЗВОДСТВО ───────────────────────┐
   │ brief-generator → бриф (pending) → brief-reviewer│
   │ → auto-approve ИЛИ решение оператора             │
   └────────────────────────┬────────────────────────┘
                            ▼
        оператор снимает и публикует ролик
                            ▼
   ┌──────────── ОБРАТНАЯ СВЯЗЬ ─────────────────────┐
   │ n8n собирает просмотры/ER → CF Performance →    │
   │ /cf-eval (еженедельно) → инсайты →              │
   │ /cf-propose-update → proposal → оператор →      │
   │ новая версия промпта (CF Prompt Versions)       │
   └─────────────────────────────────────────────────┘
```

Ключевая цепочка данных (она же «родословная» каждого ролика):

```
source_url → pattern_id → formula_id → brief_id → prompt_version → reel_id → performance
(чужой ролик) (паттерн)   (формула)    (бриф)     (версия промпта) (наш ролик) (метрики)
```

По этой цепочке можно для любого опубликованного ролика ответить: «из каких чужих
видео родился этот сценарий и как он в итоге отработал» (`python -m cf trace <brief_id>`).

## 3. Словарь терминов

### 3.1 Общие IT-термины, которые встречаются в проекте

**Репозиторий (repo)**
- 🎓 Каталог под версионным контролем git: полная история изменений, ветки, откаты.
- 🐣 Папка проекта с «машиной времени»: каждое сохранение (коммит) запоминается, можно
  посмотреть, кто что менял, и вернуться к любой версии.

**Коммит (commit)**
- 🎓 Атомарный снапшот изменений в git с сообщением и автором.
- 🐣 «Сохранение в игре» с подписью, что именно сделано.

**Pre-commit hook**
- 🎓 Скрипт, который git автоматически запускает перед созданием коммита; ненулевой
  exit code отменяет коммит. Здесь: `cf check-commit` блокирует секреты и runtime-файлы.
- 🐣 Охранник на выходе: перед каждым «сохранением» проверяет, что ты случайно не
  прикладываешь к посылке ключи от квартиры (пароли, служебные файлы).

**CLI (command-line interface)**
- 🎓 Текстовый интерфейс программы; здесь — `python -m cf <команда>` с argparse-парсером
  подкоманд (src/cf/cli.py).
- 🐣 Управление программой командами в чёрном окне терминала вместо кнопок. Как
  писать SMS-команды роботу: `cf status` — «покажи, что происходит».

**venv (виртуальное окружение)**
- 🎓 Изолированный набор Python-интерпретатора и пакетов проекта (`.venv/`), чтобы
  зависимости проектов не конфликтовали.
- 🐣 Отдельный ящик с инструментами только для этого проекта, чтобы не смешивать с
  инструментами других проектов.

**pyproject.toml / зависимости**
- 🎓 Манифест проекта: метаданные, requires-python, список библиотек (gspread, fastapi…).
- 🐣 Список покупок: какие чужие готовые библиотеки нужно поставить, чтобы проект работал.

**pytest / тесты**
- 🎓 Фреймворк модульного тестирования; в `tests/` 1031 pytest-тест (на 2026-07-24,
  включая порт всех инвариантов n8n-логики — карта в tests/test_collect_parity.py)
  с фейками вместо реального Google Sheets (tests/fakes.py); плюс 145 node-тестов
  в `n8n/__tests__/` (эталон порта до этапа 6 миграции).
- 🐣 Робот-проверяльщик: набор маленьких сценариев «если сделать X, должно получиться Y».
  Запускаешь одной командой и видишь, не сломал ли ты что-то в другом месте.

**JSON**
- 🎓 Текстовый формат сериализации структур данных (объекты/массивы/строки/числа).
- 🐣 Стандартный способ записать данные текстом так, чтобы их понимали и люди, и
  программы: `{"имя": "значение"}`. Все артефакты фабрики (паттерны, формулы, брифы)
  — это JSON-файлы.

**JSON Schema**
- 🎓 Декларативное описание допустимой структуры JSON; валидация через jsonschema
  (Draft 2020-12). Схемы лежат в `schemas/*.json`.
- 🐣 Бланк с обязательными полями: «в брифе обязан быть hook не короче 5 символов и
  хотя бы одна ссылка-референс». Если агент написал бриф без ссылки — бланк не принят,
  `cf validate brief` перечислит, что не так.

**API**
- 🎓 Программный контракт сервиса: методы, форматы запросов/ответов. Здесь: Google
  Sheets API (через gspread), n8n REST API (`/api/v1/workflows`), Apify.
- 🐣 «Окошко обслуживания» чужого сервиса для программ: не через сайт руками, а
  запросами «дай данные / запиши данные» по строгим правилам.

**Вебхук (webhook)**
- 🎓 HTTP-эндпоинт, вызов которого запускает процесс на стороне сервера; дашборд
  POST-ит `https://n8n.example.com/webhook/cf-raw-tiktok` и т.п., чтобы стартовать сбор.
- 🐣 Кнопка-звонок с URL-адресом: дёрнул ссылку — на том конце заработал конвейер.

**Эндпоинт / роут (route)**
- 🎓 Пара «HTTP-метод + путь», обрабатываемая функцией веб-приложения
  (`@app.get("/briefs")` в src/cf/dashboard/app.py).
- 🐣 Конкретный адрес внутри сайта и правило, что показать/сделать, когда на него зашли.

**GET / POST**
- 🎓 HTTP-методы: GET — идемпотентное чтение, POST — изменение состояния (формы решений
  на дашборде — только POST).
- 🐣 GET — «покажи страницу», POST — «прими моё действие» (нажатие кнопки «Одобрить»).

**FastAPI / uvicorn**
- 🎓 ASGI-фреймворк для веб-приложений на Python + ASGI-сервер, который его запускает.
  Дашборд — FastAPI-приложение на `http://127.0.0.1:8787`.
- 🐣 Конструктор, из которого собран локальный мини-сайт «пульт фабрики», и мотор,
  который этот сайт крутит у тебя на компьютере.

**Jinja2 (шаблонизатор)**
- 🎓 Движок HTML-шаблонов с подстановкой контекста, циклами и наследованием
  (`templates/*.html`, `{% block content %}`).
- 🐣 Трафарет страницы: HTML с «дырками» `{{ title }}`, в которые Python вставляет
  живые данные перед показом.

**HTMX**
- 🎓 JS-библиотека декларативного AJAX: атрибуты `hx-get`/`hx-post` обновляют фрагменты
  DOM ответами сервера без SPA-фреймворка. Дашборд перезагружает карточки конвейера
  (partials) без обновления всей страницы.
- 🐣 Хитрость, из-за которой страница обновляет свои кусочки сама (статус «выполняется…»
  оживает), хотя написана без сложного фронтенда — почти без JavaScript.

**Кеш / TTL**
- 🎓 Хранение результата дорогой операции для повторного использования; TTL — срок
  годности записи. DataCache держит строки вкладок 60 секунд (src/cf/dashboard/data.py).
- 🐣 Блокнот-шпаргалка: чтобы не бегать в Google-таблицу за одними и теми же данными
  каждую секунду, дашборд минуту пользуется записанным, потом перечитывает.

**Ретрай / экспоненциальный бэкофф**
- 🎓 Повтор операции при транзиентной ошибке с растущей задержкой (1с → 2с → 4с);
  `with_retry` в src/cf/retry.py, 4xx-ошибки (кроме 429) не ретраятся.
- 🐣 Если Google не ответил — подожди секунду и попробуй ещё раз, потом две, потом
  четыре. Но если ошибка «у тебя нет прав» — повторять бессмысленно, сразу сдаёмся.

**Идемпотентность**
- 🎓 Свойство операции давать тот же результат при повторном выполнении. Пример:
  `Sheets.append_row` при ретрае сканирует хвост листа (последние ~10 строк), чтобы не задвоить запись.
- 🐣 «Нажми кнопку лифта дважды — лифт приедет один раз». Важно при повторах после
  сбоя: чтобы бриф не записался в таблицу два раза.

**Атомарная запись**
- 🎓 Запись во временный файл + `os.replace` (src/cf/io.py): читатель никогда не видит
  полузаписанный JSON.
- 🐣 Сначала пишем письмо начисто на черновике, потом мгновенно подменяем старый лист
  новым. Никто не увидит файл «наполовину».

**Race condition (гонка)**
- 🎓 Ошибка из-за недетерминированного порядка конкурентных операций над общим
  состоянием; в раннере защита — `threading.Lock` при захвате звена (`_claim`).
- 🐣 Два повара тянутся к одной кастрюле одновременно — получится каша не по рецепту.
  Лок — это правило «кастрюлю берёт только один, второй ждёт».

**Поток (thread) / ThreadPoolExecutor**
- 🎓 Единица конкурентного выполнения внутри процесса; пул с `max_workers=2` гоняет
  прогоны ниш параллельно (runner.py).
- 🐣 Дополнительные «руки» программы: пока одна рука ждёт ответа от Claude по нише
  «обувь», вторая уже работает над «стритвиром». Больше двух рук не даём — чтобы не
  устроить бардак.

**Fan-out (фан-аут)**
- 🎓 Паттерн распараллеливания: одна задача порождает N независимых подзадач (по нише
  на воркера), результаты агрегируются.
- 🐣 Веер: вместо «сначала одна ниша, потом другая» — раздать все ниши помощникам
  сразу и собрать готовое.

**Сабпроцесс (subprocess)**
- 🎓 Дочерний процесс ОС, запущенный программой; раннер вызывает
  `claude -p "/cf-niche-run …" --output-format json` и парсит stdout.
- 🐣 Программа нанимает другую программу: дашборд буквально запускает консольного
  Claude как отдельную рабочую единицу и читает его письменный отчёт.

**Exit code (код выхода)**
- 🎓 Целое число завершения процесса: 0 — успех, ≠0 — ошибка; конвейер считает
  ненулевой код приоритетнее самоотчёта агента.
- 🐣 Оценка за смену: 0 — «всё сделал», любая другая — «был косяк», что бы работник
  ни рассказывал.

**stdout / stderr**
- 🎓 Стандартные потоки вывода процесса: результат и диагностика соответственно.
- 🐣 Два лотка у станка: в один падает продукция, в другой — жалобы и предупреждения.

**Кодировка / UTF-8**
- 🎓 Отображение символов в байты; Windows-консоль по умолчанию cp1251/cp866, поэтому
  CLI принудительно переключает stdout в UTF-8 (`force_utf8_stdio`), а все файлы
  читаются/пишутся с `encoding="utf-8"`.
- 🐣 Алфавит, которым компьютер записывает буквы числами. Если писать кириллицу одним
  алфавитом, а читать другим — получатся «кракозябры»; проект везде явно говорит
  «пиши UTF-8».

**Service account (сервисный аккаунт)**
- 🎓 Небраузерная учётка Google для машин: JSON-ключ + OAuth2-скоупы; доступ к таблице
  выдан на email сервис-аккаунта, ключ лежит в `~/.cf/secrets/service-account.json` (вне репозитория).
- 🐣 Робот-сотрудник с собственным пропуском в Google-таблицу. Пропуск (файл-ключ)
  хранится в сейфе `~/.cf/secrets/` (в домашней папке) и никогда не выкладывается в репозиторий.

**Rate limit / квота**
- 🎓 Ограничение частоты вызовов API (у Google Sheets — на запросы в минуту); при 429
  помогает ретрай с бэкоффом.
- 🐣 Турникет: «не больше N обращений в минуту». Кто ломится чаще — того просят
  подождать.

**Скрейпинг / Apify / актор**
- 🎓 Автоматизированный сбор данных с сайтов; Apify — облачная платформа, «актор» —
  её готовый скрейпер (TikTok/Instagram), которого n8n вызывает по API.
- 🐣 Робот-разведчик, который ходит по TikTok и переписывает в табличку: ссылка,
  автор, просмотры, текст под видео, субтитры.

**n8n / low-code**
- 🎓 Self-hosted платформа автоматизаций: воркфлоу из узлов (HTTP, Sheets, Code)
  с krón/webhook-триггерами; наш инстанс — n8n.example.com, воркфлоу версионируются
  в `n8n/` через pull-n8n/push-n8n.
- 🐣 Конструктор «если это — сделай то» из кубиков, почти без программирования.
  Кубики соединяются стрелочками: «каждое утро → спроси Apify → отфильтруй → запиши
  в таблицу».

**Слаг (slug)**
- 🎓 Строка-идентификатор из безопасных символов (`re.sub(r'[^\w-]+', '-', …)`) для
  имён файлов/URL; так «мужской-стиль» попадает в имя файла отчёта.
- 🐣 Название, «почищенное» для файла: без пробелов, кавычек и прочего, что бесит
  файловую систему.

**Дедупликация (дедуп)**
- 🎓 Устранение повторов по ключу; здесь — по `source_url`, с приоритетом строки с
  транскриптом, затем более свежей (analyze.dedupe_rows).
- 🐣 Один и тот же ролик мог попасть в таблицу дважды (по хэштегу и по поиску) —
  считаем его один раз, оставляя самую полную запись.

**Парсинг**
- 🎓 Разбор текста в структуру данных (например, `NICHE_RESULT: {...}` из stdout агента).
- 🐣 Чтение с выделением главного: из простыни текста выковырять нужные цифры.

**Frontmatter**
- 🎓 YAML-шапка между `---` в начале Markdown-файла с метаданными (status, prompt_id);
  у proposals парсится мини-парсером в sections.py.
- 🐣 «Паспортные данные» документа в самом его начале: статус, дата, к какому промпту
  относится.

**TF-IDF**
- 🎓 Векторизация текста: вес слова = частота в документе × редкость по корпусу;
  используется в cluster.py для группировки «other»-роликов.
- 🐣 Способ понять, о чём текст: часто встречающиеся именно в этом тексте слова важнее,
  чем слова, которые есть везде («и», «в», «на» не считаются).

**Косинусное сходство**
- 🎓 Мера близости векторов по углу (0..1); порог 0.25 склеивает похожие ролики в кластер.
- 🐣 Насколько два текста «смотрят в одну сторону»: про кроссовки и про кеды — близко,
  про кроссовки и про заправки — нет.

**Квартиль / медиана**
- 🎓 Порядковые статистики: медиана — середина распределения, четверти — квартили;
  анализ берёт верхнюю четверть по ER как winners, нижнюю — losers.
- 🐣 Выстроили ролики в шеренгу по успешности: середина шеренги — медиана, первые 25% —
  отличники (winners), последние 25% — двоечники (losers).

**ER (engagement rate)**
- 🎓 (лайки+комменты+шеры+сохранения)/просмотры; считается в analyze.engagement_rate,
  ролики с 0 просмотров помечаются аномалиями.
- 🐣 Доля зрителей, которые не просто посмотрели, а отреагировали. 100 000 просмотров
  и 3 лайка — «пустые» просмотры; ER это ловит.

**Human-in-the-loop**
- 🎓 Архитектура, в которой критические переходы состояния требуют явного решения
  человека; здесь — утверждение формул, ревью брифов (кроме auto-approve по строгим
  условиям), применение proposals.
- 🐣 Автопилот ведёт, но ручку газа держит человек: машина готовит и советует,
  «печать» ставит оператор.

**Evidence-first**
- 🎓 Железное правило №1: любой вывод агента обязан ссылаться на данные (source_urls,
  метрики); артефакт без evidence не создаётся.
- 🐣 «Не веришь — покажи чек»: паттерн не существует, если нет списка конкретных
  роликов-доказательств с цифрами.

### 3.2 Термины самой фабрики

**Raw (сырьё, raw-строки)**
- 🎓 Неочищенные записи собранных видео во вкладках CF Raw TikTok / CF Raw Instagram:
  source_url, account, views, лайки/комменты/шеры/сейвы, caption, transcript_text,
  posted_at, raw_json Apify-итема, source_query, niche (заполняется классификатором).
- 🐣 Улов разведчиков: по строке на каждый найденный чужой ролик со всеми его цифрами
  и текстами. Пока это просто куча — смысл появится после анализа.

**Батч (batch)**
- 🎓 Порция raw-строк, обрабатываемая за один прогон (обычно вкладка+ниша+период).
- 🐣 Один противень из печки: анализируем не по ролику, а партиями.

**Ниша (niche)**
- 🎓 Категория контента из таксономии `prompts/agents/niche-taxonomy.json` (12 ниш:
  мужской-стиль, мужские-образы, стритвир, обувь…); присваивается классификатором
  по содержанию, а не по хэштегам.
- 🐣 Полка, на которую кладём ролик: «про мужской стиль», «про кроссовки». Важно:
  полку выбираем по тому, что в ролике на самом деле, а не по наклейкам-хэштегам.

**Таксономия**
- 🎓 Закрытый список допустимых ниш; единственный источник истины — niche-taxonomy.json,
  расширяется только решением оператора (кнопка на дашборде из предложений кластеризации).
- 🐣 Утверждённый список полок. Новую полку не заводят самовольно — сначала
  предложение, потом решение хозяина.

**Other / кластер**
- 🎓 Ниша-отстойник для неклассифицируемого; при other >30% батча `cf cluster-other`
  строит TF-IDF-кластеры, классификатор превращает крупные (≥30 строк) в предложения
  новых ниш (`agent-runtime/niche-proposals/`).
- 🐣 Коробка «разное». Когда она распухает, машина раскладывает содержимое на кучки
  похожего и спрашивает: «может, заведём полку под это?»

**Паттерн (pattern)**
- 🎓 Верифицированное наблюдение «что отличает winners от losers» с evidence
  (≥3 source_urls, avg_views, avg_er) и confidence high/medium; JSON в
  `agent-runtime/patterns/`, по schemas/patterns.schema.json.
- 🐣 Подмеченная закономерность: «ролики, где автор говорит от первого лица о своей
  системе, стабильно залетают лучше лекций стилиста» — плюс список роликов-доказательств.

**Формула (formula)**
- 🎓 Переиспользуемый шаблон контента, выведенный из паттернов: hook_structure,
  problem_definition, solution_structure, visual_requirements, cta_type, prohibitions,
  conditions, evidence; lifecycle proposed → approved → paused/rejected; JSON+MD в
  `formulas/{ниша}/`, approved-индекс — `formulas/_approved/index.json`.
- 🐣 Рецепт ролика: с чего начать первые 5 секунд, как строить середину, чем закончить,
  чего не делать никогда — с доказательствами, что рецепт работает. Формула — главный
  «товар» аналитической части фабрики.

**Бриф (brief)**
- 🎓 Конкретный сценарий ролика, сгенерированный по формуле и промпту ниши: hook,
  script, visual_direction, cta, references; JSON по schemas/brief.schema.json, строка
  в CF Creative Briefs со статусом ревью.
- 🐣 Готовое задание на съёмку: что сказать в первые секунды, о чём ролик, как снять,
  какие чужие ролики посмотреть для образца. Оператор берёт бриф — и просто снимает.

**Референс (reference)**
- 🎓 URL чужого ролика из evidence формулы/паттерна, подтверждённый транскриптом или
  однозначным капшеном; бриф обязан демонстрировать приём, реально присутствующий в
  референсах (цитаты — в `agent-runtime/briefs/{brief_id}-evidence.md`).
- 🐣 Образец «смотри, как надо»: живой ролик, где приём из сценария реально показан.
  Не декорация — доказательство.

**Hook (хук)**
- 🎓 Структура первых 0–5 секунд ролика (timing + elements в hook_structure формулы).
- 🐣 Крючок: первые секунды, из-за которых зритель не пролистывает.

**CTA (call to action)**
- 🎓 Целевое действие, к которому подводит ролик (cta_type формулы: «сохрани»,
  «подпишись на part N+1»…).
- 🐣 Просьба в конце: что зритель должен сделать после просмотра.

**Prohibitions (запреты)**
- 🎓 Выведенные из losers анти-паттерны формулы; нарушение в скрипте брифа = reject
  на ревью.
- 🐣 Список «так не делай» с примерами провалившихся роликов, которые так делали.

**Prompt version (версия промпта)**
- 🎓 Запись в CF Prompt Versions: prompt_id (например `brief-мужские-образы-reel`),
  version, github_path, active=TRUE/FALSE; активацию пишет `cf log-prompt-version`,
  деактивируя предыдущую. Каждый бриф несёт prompt_version — это ось A/B-сравнения в eval.
- 🐣 Номер редакции инструкции для агента-сценариста. Меняем инструкцию → новый номер →
  потом можно честно сравнить: сценарии по какой редакции залетали лучше.

**Proposal**
- 🎓 Evidence-backed предложение изменения: промпта (`proposals/*.md` с diff и
  метриками) или списков источников (`proposals/*-sources-*.json` по
  source-proposal.schema.json). Применяется только человеком.
- 🐣 Служебная записка от машины: «предлагаю поправить инструкцию вот так, потому что
  вот цифры». Начальник читает и решает.

**Run Log (CF Run Log)**
- 🎓 Журнал запусков всех агентов: run_id, agent, status
  (success/failed/insufficient_data), input_summary, output_paths, errors, trigger_type;
  пишется `cf log-run` / автоматически из CLI и дашборда.
- 🐣 Вахтенный журнал фабрики: кто, когда, что делал и чем кончилось. Первое место,
  куда смотрим при вопросе «а что вообще происходило?»

**Ingestion Gate (гейт сбора)**
- 🎓 Code-узел в каждом CF01-воркфлоу: дропает рекламу, блок-лист авторов (wb.* и
  явный список), языки не ru/en/un, >9 хэштегов в капшене, посты старше 30 дней и
  «залежавшиеся» (<500 просмотров при возрасте >14 дней); счётчики дропов — в
  execution-логе n8n.
- 🐣 Фейс-контроль на входе: рекламу, барахолки и протухшие ролики разворачиваем ещё
  до того, как тратить деньги на субтитры и место в таблице.

**Атрибуция / source_query**
- 🎓 Метка происхождения каждой raw-строки: `hashtag:#x` / `query:x` /
  `snowball:<seed_url>` / `unknown`; позволяет считать yield источников
  (source-stats) и тюнить списки сбора.
- 🐣 Бирка «откуда улов»: с какого хэштега или поискового запроса пришёл ролик.
  Без бирки нельзя понять, какие сети приносят рыбу, а какие — мусор.

**Snowball (снежный ком)**
- 🎓 Воркфлоу CF01b (еженедельно, вс 09:00): по seed-URL из CF Seeds тянет related
  videos через Apify — сбор расширяется от подтверждённых winners.
- 🐣 От хорошего ролика катимся к его «родственникам»: TikTok сам подсказывает похожие
  видео, и среди них часто такие же удачные.

**Seed (затравка)**
- 🎓 Winner-URL из evidence approved-формул, выгруженный `cf export-seeds` во вкладку
  CF Seeds (seed_type=winner, active=TRUE).
- 🐣 Снежинка, с которой начинают катить ком: проверенно успешный ролик.

**Конвейер / звено (stage)**
- 🎓 Оркестрация в дашборде (runner.py): звенья raw (вебхуки сбора + ожидание
  прироста), factory (фан-аут агентов), publish, stats (вебхуки n8n); автоцикл —
  raw → factory, дальше ждёт человека.
- 🐣 Кнопки-этапы на пульте: «привези сырьё», «включи завод», «опубликуй», «сними
  метрики». Кнопка «Прокрутить цикл» жмёт первые две по очереди сама.

**Фан-аут «Контент-завода» (звено factory)**
- 🎓 Последовательность: /cf-classify-niche → очередь ниш (дедуп-строк с
  views≥min_views не меньше min_rows и ≥min_new_rows новых строк с прошлого анализа) → пул из
  workers×`claude -p /cf-niche-run` → /cf-generate-briefs → /cf-review-brief --pending
  → formula-guard → git commit formulas/. Пороги — cf.config.json → dashboard.fanout.
- 🐣 Одна кнопка, за которой целая смена: разложить новые ролики по полкам, для каждой
  «созревшей» полки запустить аналитика, собрать рецепты, написать сценарии, отревьюить
  их и сохранить результат. На экране живой счётчик «ниши 2/3 · формул 1».

**NICHE_RESULT**
- 🎓 Контракт агента ниши с раннером: последняя строка stdout
  `NICHE_RESULT: {"status": …, "patterns": N, "formulas": M}` — печатается при любом
  исходе, парсится `_parse_niche_result`.
- 🐣 Обязательная последняя строка отчёта работника: «итог смены: столько-то рецептов».
  Без неё пульт считает, что рецептов ноль.

**Лаборатория (страница /lab)**
- 🎓 Раздел дашборда: очередь proposed-формул с кнопками решения, paused-формулы,
  предложения ниш, версии промптов, паттерны, proposals, последний weekly-eval.
- 🐣 Комната, где лежит всё, что машина предлагает человеку решить: новые рецепты
  «подпиши или отклони», идеи новых полок, отчёты об экспериментах.

**insufficient_data**
- 🎓 Валидный терминальный статус любого шага при нехватке данных (правило №2):
  отчёт со списком недостающего вместо выводов «на глаз».
- 🐣 Честное «данных мало, выводов не будет — вот чего не хватает». Это не ошибка,
  это нормальный ответ; хуже была бы уверенная выдумка.

**Auto-approve**
- 🎓 `cf auto-approve <brief_id> --review <файл>`: одобрение брифа без оператора при
  4 условиях — вердикт ревьюера recommend, формула в approved-индексе, активный промпт
  `brief-{niche}-reel`, кап <5 approved-брифов формулы за 7 дней. Иначе — остаётся
  pending с печатью причины.
- 🐣 Зелёный коридор: если проверяющий сказал «рекомендую», рецепт утверждён,
  инструкция актуальна и мы не завалили съёмочную группу — бриф проходит сам, без
  начальника.

**Formula-guard**
- 🎓 `cf formula-guard`: по каждой approved-формуле смотрит последние 5 брифов;
  ≥3 rejected → формула paused и выходит из approved-индекса (авто-пауза), запись в
  Run Log. Запускается в конце фан-аута как страховка.
- 🐣 Предохранитель: если по рецепту три из пяти последних сценариев забракованы —
  рецепт снимается с производства сам, не дожидаясь, пока человек заметит.

**agent-runtime/**
- 🎓 Негитуемый каталог runtime-артефактов (правило №4): profiles, analysis, patterns,
  briefs, niches, clusters, niche-proposals, evals, source-stats, reviews. Версионируются
  только prompts/, formulas/, proposals/, schemas/, .claude/.
- 🐣 Рабочий стол фабрики: черновики и отчёты текущей работы. В «архив с историей»
  (git) попадают только чистовики — рецепты, инструкции, решения.

**Память агентов (.claude/memory/)**
- 🎓 Файловая память: patterns/{niche}-observations.md (наблюдения анализа),
  decisions/ (решения оператора, в т.ч. авто-файлы одобрения формул с дашборда),
  evaluations/ (инсайты eval); индекс MEMORY.md — по строке на файл.
- 🐣 Дневник фабрики: что подметили, что решили и почему. Новый агент читает дневник
  и не наступает на старые грабли.

## 4. Архитектура: три слоя и пульт

### Слой 1 — n8n (runtime, «руки»)
Живёт на `n8n.example.com`. Агентами не заменяется (граница слоя): его зона —
ежедневный сбор raw и performance. Оговорка: решением 2026-07-22 система переезжает
на собственный VPS, n8n выводится после приёмки (см. docs/BUSINESS-CONTEXT.md).
Воркфлоу версионируются в `n8n/<slug>/`
(workflow.json + код Code-узлов в `code/*.js`), правки — только через
`cf pull-n8n` / `cf push-n8n`, не в UI.

| Воркфлоу | Что делает | Запуск |
|---|---|---|
| CF 01 TikTok (`n8n/cf01-tiktok/`) | Apify-скрейп по SOURCES (хэштеги+запросы) → Ingestion Gate → транскрипты → CF Raw TikTok | ежедневно + вебхук `cf-raw-tiktok` |
| CF 01 Instagram (`n8n/cf01-instagram/`) | то же для Instagram → CF Raw Instagram | ежедневно + вебхук `cf-raw-instagram` |
| CF 01b Snowball (`n8n/cf01b-snowball/`) | related videos от seed-URL из CF Seeds → тот же гейт → CF Raw TikTok | вс 09:00 + вебхук `cf-snowball-tiktok` |
| CF 04 Performance (`n8n/cf04-performance/`) | метрики опубликованных роликов → CF Performance | вручную + вебхук `cf-stats` (крона нет) |

### Слой 2 — Claude Code (intelligence, «мозг»)
Агенты = промпты в `prompts/agents/*.md` + slash-команды в `.claude/commands/`.
Детерминированную математику (квартили, дедуп, пороги) считает CLI — агент делает
только смысловую часть. Подробно — [раздел 6](#6-агенты).

### Слой 3 — хранилища
- **Google Sheets** — операционная «база данных» (8 вкладок: CF Raw TikTok, CF Raw
  Instagram, CF Creative Briefs, CF Published Reels, CF Performance, CF Prompt
  Versions, CF Run Log, CF Seeds). Имена колонок n8n маппятся на канонические через
  `column_aliases` в cf.config.json (url→source_url, author→account…).
- **Git** — версионируемое хранилище знаний: prompts/, formulas/, proposals/,
  schemas/, .claude/ (память и команды).
- **agent-runtime/** — локальные runtime-артефакты (вне git).
- **~/.cf/secrets/** — ключ сервис-аккаунта, API-ключ n8n и webhook-token.txt (в домашней папке, вне репозитория; пути заданы в cf.config.json).

### Пульт — дашборд (`python -m cf dashboard`, http://127.0.0.1:8787)
| Страница | Что на ней |
|---|---|
| Обзор | метрики за 7/30/90 дней (raw, брифы, pending, опубликовано, средний ER, ER по неделям), карточки конвейера с кнопками звеньев и «Прокрутить цикл», отчёты агентов с формой ответа (resume сессии Claude), health-панель |
| Брифы | список с фильтрами по статусу, карточка брифа, «происхождение» (формула → паттерны → evidence, совпадение референсов), кнопки Одобрить/Отклонить/Вернуть в pending |
| Перформанс | вкладки «Ролики» (CF Published Reels) и «Метрики» (CF Performance) |
| Запуски | последние 100 записей CF Run Log с бейджами статусов |
| Лаборатория | очередь proposed-формул (кнопки approve/reject/pause), paused-формулы, предложения ниш (accept/reject), версии промптов, паттерны, proposals, последний eval |
| Источники | последние 200 raw-строк по вкладке TikTok/Instagram |

Инфраструктура пульта: DataCache (TTL 60 с, при сбое Sheets отдаёт старые данные с
пометкой stale), HealthMonitor (раз в 60 с: чтение Sheets, `GET /healthz` n8n,
наличие `claude` в PATH), StageRunner (звенья и фан-аут). Решения с кнопок пишут
файлы репозитория и коммитят через единственную git-точку (агентам git запрещён).

## 5. Путь одной единицы контента (сквозной пример)

1. **Понедельник, 09:00.** n8n CF 01 спрашивает Apify по хэштегу `#мужскойстиль`.
   Среди улова — ролик `tiktok.com/@_zachmcnally/video/766…`: 184К просмотров, автор
   рассказывает свою систему подбора стиля. Ingestion Gate пропускает (не реклама,
   свежий, язык en), строка ложится в **CF Raw TikTok** с `source_query=hashtag:#мужскойстиль`.
2. **Оператор жмёт «Прокрутить цикл»** (или звено «Контент-завод»). `/cf-classify-niche`
   читает caption+транскрипт → `niche=мужской-стиль` (по контенту: мужская одежда на
   мужчине, не по хэштегу).
3. В нише накопилось 14 дедуп-строк с ≥1000 просмотров и рост с прошлого анализа ≥1.5× —
   ниша попадает в очередь фан-аута. Воркер запускает `claude -p "/cf-niche-run
   raw_tiktok мужской-стиль"`.
4. Внутри прогона: `cf profile` (батч чистый) → `cf analyze-batch` (медиана просмотров,
   winners — верхняя четверть по ER, losers — нижняя) → агент формулирует **паттерн**
   `muzhskoy-stil-tt-personal-system-01` («личная система автора против лекции
   стилиста»), верифицируя каждый URL по транскрипту → из паттерна пишет **формулу**
   `personal-style-system` со `status: proposed` → печатает `NICHE_RESULT: {...}`.
5. **Лаборатория.** Оператор видит формулу в очереди, читает hook/запреты/evidence
   (4 URL, avg ER 0.174) и жмёт **Approve**: JSON получает `status: approved`, попадает
   в `formulas/_approved/index.json`, пишется decision-файл в память, git-коммит.
6. `/cf-generate-briefs`: по формуле и активному промпту `brief-мужской-стиль-reel`
   (промпт заводится на нишу: `prompts/briefs/{ниша}/reel.md` + активация версии;
   сейчас реальный промпт есть только у «мужские-образы» — для новой ниши его нужно
   сначала создать) генерирует до 2 брифов, сначала отобрав референсы (каждый подтверждён транскриптом),
   цитаты — в evidence-файл; `cf add-brief` валидирует по схеме и пишет **pending**-строку
   в CF Creative Briefs.
7. `/cf-review-brief --pending`: ревьюер прогоняет 7 проверок (схема, соответствие
   формуле, запреты, референсы↔скрипт, ниша/пол, снимаемость, связь с продуктом) →
   вердикт recommend → `cf auto-approve b-personal-style-system-20260720-a --review …`:
   все 4 условия выполнены → **approved** без участия человека (или остаётся pending
   с причиной — тогда решает оператор кнопкой на «Брифах»).
8. **Оператор снимает ролик по брифу**, публикует, вносит строку в CF Published Reels
   (reel_id, brief_id, дата, production_notes).
9. n8n CF 04 (запуск вручную или вебхуком `cf-stats`) дописывает метрики ролика в
   **CF Performance** (views, ER).
10. **Воскресенье.** `/cf-eval`: `cf eval-prep` собирает датасет, агент связывает
    performance с prompt_version и формулами, атрибутирует провалы
    (prompt/reference/production/publishing), пишет weekly-eval и инсайты в память.
    При системных reject'ах `/cf-propose-update` готовит **proposal** с diff промпта
    и цифрами; оператор одобряет → `cf log-prompt-version --candidate` заводит v2 как
    candidate (активная версия не гасится), брифы чередуют версии по `cf ab-plan`
    (interleaving) — сравнение по-честному. Круг замкнулся.

## 6. Агенты

«Агент» здесь — это промпт-инструкция (prompts/agents/*.md), которую исполняет Claude
Code при вызове slash-команды. Детерминированная механика вынесена в CLI — агент
отвечает за смысл. У каждого агента статус запуска пишется в Run Log.

### 6.1 Аналитическая линия

**Niche Classifier** (`/cf-classify-niche`, prompts/agents/niche-classifier.md)
- 🎓 Классификация raw-строк с пустой niche по caption+transcript в закрытую таксономию;
  режимы ре-аудита и кластеризации (`--clusters` → предложения ниш из cluster-other).
  Пишет mapping в agent-runtime/niches/, применяет `cf apply-niches` (одна батч-запись
  колонки).
- 🐣 Сортировщик: раскладывает свежие ролики по полкам-нишам, глядя на содержание, а
  не на хэштеги. Сомнительное — в коробку «other»; когда коробка распухла, предлагает
  завести новые полки.

**Raw Batch Profiler** (`/cf-profile`, prompts/agents/raw-batch-profiler.md)
- 🎓 Обёртка над `cf profile`: интерпретация отчёта качества (дубли, пропуски
  критических полей, порог ≥20 чистых строк → ready_for_analysis).
- 🐣 ОТК сырья: «этой партией можно кормить аналитика или сначала дособрать/починить
  данные?». Честно говорит «мало данных», когда мало.

**Pattern Analyzer** (`/cf-analyze`, prompts/agents/pattern-analyzer.md)
- 🎓 Смысловой слой над `cf analyze-batch` (метод v2): формулирует паттерны из
  winners/losers/same_account (сигнал ≥3 winners и отличие от losers), обязательная
  верификация каждого evidence-URL по транскрипту, confidence high/medium/low
  (low — только в память), конфликтующие паттерны — оба с conditions.
- 🐣 Детектив: смотрит на отличников и двоечников одной ниши и называет, ЧТО именно
  отличники делают иначе. Каждую догадку обязан подтвердить конкретными роликами —
  иначе догадка не считается.

**Formula Writer** (`/cf-formula`, prompts/agents/formula-writer.md)
- 🎓 Паттерны (confidence ≥ medium) → формулы со status=proposed: hook/problem/solution/
  visual/cta/prohibitions/conditions, evidence наследуется и перепроверяется (≥3 URL);
  обновление существующей формулы (version+1) вместо дубликата; утверждение — не его
  работа.
- 🐣 Технолог: превращает подмеченные закономерности в внятный рецепт «как готовить
  такие ролики». Рецепт кладёт на стол оператору — сам в производство не запускает.

**Niche Pipeline** (`/cf-niche-run <tab> <niche>`, .claude/commands/cf-niche-run.md)
- 🎓 Композитная команда для фан-аута: profile → analyze-batch → паттерны → черновики
  формул → log-run → NICHE_RESULT (контракт с раннером). Ранний стоп на
  insufficient_data — валидный исход.
- 🐣 «Смена под ключ» по одной полке: проверка сырья, анализ, рецепты — и короткий
  итоговый рапорт последней строкой.

### 6.2 Производственная линия

**Brief Generator** (`/cf-generate-briefs`, prompts/agents/brief-generator.md)
- 🎓 По approved-индексу и активному промпту ниши (`brief-{niche}-reel`) генерирует до
  briefs_per_formula брифов на формулу, ротируя tested_variable; сначала референсы
  (верификация транскриптом, цитаты в evidence-файл), потом скрипт; кап: формула с ≥5
  approved за 7 дней пропускается; запись через `cf add-brief` (схема + pending).
- 🐣 Сценарист: берёт утверждённый рецепт, находит живые ролики-образцы и пишет
  задание на съёмку. Не набрал доказательств-образцов — честно отказывается писать
  сценарий: плохой бриф дороже, чем его отсутствие (его же реально снимут!).

**Brief Reviewer** (`/cf-review-brief`, prompts/agents/brief-reviewer.md)
- 🎓 7 проверок по строгости: схема → соответствие формуле (hook/prohibitions/cta) →
  качество референсов → смысловой матч референс↔скрипт по транскриптам → пол/ниша →
  producibility → связь с продуктом. Вердикты recommend/revise/reject; причины —
  каноническими формулировками (сырьё для Prompt Optimizer); approved сам не ставит —
  только через auto-approve.
- 🐣 Приёмщик: прогоняет каждый сценарий по чек-листу из 7 пунктов. «Рекомендую» —
  и сценарий идёт по зелёному коридору; «переделать»/«брак» — с конкретной причиной,
  всегда одними и теми же словами (чтобы потом посчитать, какая ошибка повторяется).

### 6.3 Линия обучения

**Eval Agent** (`/cf-eval`, prompts/agents/eval-agent.md)
- 🎓 Еженедельно: датасет из eval-prep (performance×briefs×prompt_versions) →
  by_prompt_version, formula_performance, атрибуция underperforming-роликов
  (views <0.5× медианы своей версии; категории prompt/reference/production/publishing
  с приоритетом prompt), success criteria (reviewer_pass_rate ≥0.8 и др.), insights
  с reel_id → weekly-eval.json + память. <5 замеренных reels на каждую сравниваемую
  версию → insufficient_data (P5.9).
- 🐣 Аналитик итогов недели: что залетело, что провалилось и ПОЧЕМУ — «сценарий был
  слабый», «образцы подвели», «съёмка не по брифу» или «не в то время запостили».
  Каждый вывод — с номером ролика и цифрами, без «в целом норм».

**Prompt Optimizer** (`/cf-propose-update`, prompts/agents/prompt-optimizer.md)
- 🎓 Генерирует proposals/*.md: дословный diff текущего промпта + evidence (rejection
  reasons с частотами, метрики версий, паттерны) + confidence + риски. Одно proposal =
  один промпт; без evidence — insufficient_data. Применение и активация — оператором.
- 🐣 Рационализатор: «эта ошибка повторилась 6 раз — предлагаю вписать в инструкцию
  вот эту строку, вот расчёты». Сам инструкции не трогает никогда.

**Source Tuner** (`/cf-tune-sources`, prompts/agents/source-tuner.md)
- 🎓 Еженедельный скоринг source_query по source-stats: кандидаты на удаление
  (rows≥20, target_yield<0.1, нет winners в формулах), на добавление
  (candidate_hashtags count≥3, не мусор); ≤5+5 за proposal
  (source-proposal.schema.json). Цепочка применения: apply-sources → push-n8n → commit.
- 🐣 Завхоз рыболовных сетей: раз в неделю смотрит, какие хэштеги приносят целевые
  ролики, а какие — хлам, и пишет записку «эти сети выбросить, эти закинуть». Менять
  сети сам не имеет права.

### 6.4 Механические «агенты» (без LLM, чистый CLI)

| Кто | Что делает |
|---|---|
| `cf auto-approve` | зелёный коридор брифа по 4 условиям (см. словарь) |
| `cf formula-guard` | авто-пауза формулы при 3 reject из последних 5 |

| `dashboard-review/formula/niche` | решения кнопками (ревью брифа, формула, ниша) |

## 9. Железные правила (CLAUDE.md, растолкованные)

1. **Evidence-first.** Ни один паттерн/формула/proposal не существует без ссылок на
   конкретные данные. *Зачем:* LLM умеет убедительно выдумывать; ссылки делают выдумку
   проверяемой и потому невозможной.
2. **insufficient_data — честный ответ.** *Зачем:* решение «подождать данных» дешевле
   решения по шуму.
3. **Human-in-the-loop для промптов.** Только proposal → ревью → применение + commit.
   *Зачем:* промпты — «прошивка» фабрики; самомодификация без ревью = неуправляемый дрейф.
4. **Runtime-артефакты только в agent-runtime/** (вне git). *Зачем:* история проекта —
   про знания, а не про тонны черновиков.
5. **Секреты не коммитятся.** secrets/ в .gitignore + pre-commit guard (`cf check-commit`
   блокирует и по путям, и по маркерам приватных ключей в содержимом staged-блобов).
6. **Каждый запуск агента логируется** в CF Run Log. *Зачем:* без журнала нельзя ни
   дебажить, ни считать eval, ни доверять системе.

Дополнительные границы: git-команды агентам запрещены (коммитят только раннер и кнопки
решений); n8n правится только через репозиторий; воркеры фан-аута не пересчитывают
статистику руками — только CLI.

  отношения не имеет — это отдельный разбор дизайн-языка стороннего продукта Sentry
  (фиолетово-лаймовая гамма dev-tools), референс-артефакт; при чистке репозитория —
  кандидат на удаление (см. docs/AUDIT-2026-07.md, раздел «Мёртвый груз»).
- **🐣 Новичок:** это «конституция внешнего вида» бренда: какие цвета можно, какие
  шрифты и размеры, как выглядят кнопки и карточки. Дашборд фабрики нарисован строго
  по ней — поэтому выглядит фирменно, а не как «админка по умолчанию». Там же —
  скрипты-проверяльщики: «не пролез ли в вёрстку чужой цвет».

## 14. FAQ

**Почему Google Sheets, а не «настоящая» база данных?**
Потому что оператор живёт в таблице: глазами видно всё состояние, можно руками
поправить, n8n пишет туда нативно. Слабые места (квоты API, отсутствие транзакций)
прикрыты ретраями, кешем и идемпотентным append. При росте объёмов миграция возможна —
весь доступ идёт через один модуль sheets.py.

**Почему брифы генерирует Claude, а не n8n с OpenAI-нодой?**
Решение оператора 2026-07-10: генерация переехала в агентскую систему (контекст,
верификация референсов, память). Старый CF 03 в n8n устарел, его JSON лежит в
docs/n8n-archive как история.

**Что будет, если данных мало?**
Любой шаг честно останавливается со статусом insufficient_data и списком недостающего.
Это норма жизни системы, а не сбой.

**Может ли система сама испортить свои промпты?**
Нет. Агенты пишут только proposals; применение — руки оператора + git-коммит. Плюс
pre-commit guard не пустит в git секреты и runtime-мусор.

**Откуда система знает, что формула «умерла»?**
Два контура: formula-guard (3 reject из 5 последних брифов → авто-пауза) и
еженедельный eval (verdict по formula_performance).

**Что такое «звено ждёт продюсера»?**
Автоцикл прокручивает только raw → factory. Публикация и метрики требуют человека
(снять ролик) — конвейер честно останавливается и пишет «цикл дошёл до ручного
одобрения».
