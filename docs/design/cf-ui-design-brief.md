# Content Factory — дизайн-бриф для UI

> Самодостаточный контекст проекта для дизайн-сессии (Claude Design).
> Основан на утверждённых решениях discovery-интервью 2026-07-11 (секции 1–2).

## Что за продукт

**Content Factory (CF)** — «контент-завод»: система, которая анализирует успешные
короткие видео (TikTok / Instagram Reels), находит в них паттерны, выводит формулы
успеха и генерирует по ним брифы (ТЗ) для съёмки собственных роликов. После
публикации собирается performance и цикл повторяется.

Конвейер по этапам:

1. **Сбор raw-видео** — n8n автоматически собирает чужие успешные ролики.
2. **Профилирование батча** — проверка качества собранных данных.
3. **Анализ паттернов** — что общего у успешных роликов ниши.
4. **Формула** — паттерны сворачиваются в формулу успеха.
5. **Генерация брифов** — по формуле создаются ТЗ для креаторов.
6. **Ревью брифов** — человек утверждает / отправляет на доработку / отклоняет.
7. **Продакшн и публикация** — креаторы снимают по ТЗ, ролики публикуются.
8. **Eval** — еженедельная оценка performance, выводы возвращаются в систему.

Этапы 2–6 и 8 выполняют ИИ-агенты на сервере; между этапами стоят **ворота
утверждения** — конвейер останавливается и ждёт решения человека.

## Пользователи

| Роль | Кто это | Что делает в UI |
|---|---|---|
| **Продюсер** (главный пользователь) | Нанимаемый сотрудник, **нетехнический** | Запускает конвейер целиком или по этапам, ведёт очередь брифов, утверждает/отклоняет, копирует ТЗ для креаторов |
| **Админ** (владелец) | Тех-специалист | Всё то же + служебный срез: интеграции, промпты, ошибки |

Ключевое следствие для дизайна: интерфейс для продюсера — без технического
жаргона, статусы человеческим языком (по-русски), крупные однозначные действия.

## Экраны (утверждены, 4 шт.)

1. **Обзор конвейера** — этапы конвейера со счётчиками объектов и метками
   «ждёт действия»; сразу видно, где конвейер остановился и что требуется.
2. **Очередь брифов** — таблица (дата / ниша / статус) + карточка брифа
   с воротами утверждения: утвердить / на доработку / отклонить,
   производственные статусы (новое для системы — см. оговорку в
   project-брифе), кнопка «скопировать ТЗ» для передачи креатору.
3. **Запуски** — «запустить всё» / запустить отдельный этап, живой ход
   выполнения текущего запуска, история запусков.
4. **Служебный (админ)** — статусы интеграций (Google Sheets, n8n),
   версии промптов, ошибки.

Референс: кликабельный макет этих экранов — опубликованный артефакт
(в витрине отсутствует; уже на 2026-07-22 был недоступен — not found).

## UX-принцип ворот утверждения

Перед каждым вопросом оператору интерфейс обязан показать:
1. **что сделано** (результат этапа),
2. **где прочитать подробности** (ссылка на документ/бриф — первым),
3. **последствия каждого варианта** выбора.

Никаких «утвердить?» без контекста.

## Словарь и статусы

- **Бриф** — ТЗ на ролик. Статусы ревью: `pending` (ждёт ревью) →
  `approved` / `revised` (на доработку) / `rejected`.
- **Ниша** — тематика контента (утверждённая таксономия).
- **Паттерн → формула → бриф** — цепочка происхождения: каждый бриф
  сгенерирован по формуле, формула выведена из паттернов, паттерны — из
  конкретных роликов (везде evidence-ссылки).
- **Запуск (run)** — одно выполнение агента/этапа; статусы:
  `success` / `insufficient_data` / `failed` (в UI `failed` — «Ошибка»).
- **insufficient_data** — честный статус «данных мало, вывода нет»; в UI это
  нормальное состояние, а не ошибка.
- **Performance** — метрики опубликованного ролика (просмотры, ER).

## Технические ограничения (влияют на дизайн-систему)

- Стек: **FastAPI + HTMX**, server-rendered HTML. Никакого SPA/React.
- Дизайн-система должна быть реализуема простым HTML + CSS
  (компоненты — серверные шаблоны, интерактив — HTMX-паттерны).
- Источник данных — Google Sheets; данные табличные, UI много работает
  со списками/таблицами и карточками.
- Язык интерфейса — русский.
