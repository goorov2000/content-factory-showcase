# Content Factory — бриф на веб-интерфейс (самодостаточный контекст проекта)

Ты помогаешь построить веб-интерфейс для существующего проекта. Ниже — всё, что нужно знать о проекте: у тебя нет доступа к его репозиторию и данным, поэтому весь контекст в этом документе. Дизайн (цвета, шрифты, стилистика) в этом брифе намеренно не описан — сосредоточься на структуре, экранах и логике.

## 1. Что за продукт

**Content Factory (CF)** — «контент-завод»: система, которая анализирует чужие успешные короткие видео (TikTok / Instagram Reels), находит в них паттерны, сворачивает паттерны в «формулы успеха» и генерирует по формулам брифы (ТЗ) на съёмку собственных роликов. После публикации собираются метрики (performance), и цикл повторяется.

Конвейер по этапам:

1. **Сбор raw-видео** — n8n автоматически собирает чужие успешные ролики.
2. **Профилирование батча** — проверка качества собранных данных.
3. **Анализ паттернов** — что общего у успешных роликов ниши.
4. **Формула** — паттерны сворачиваются в формулу успеха.
5. **Генерация брифов** — по формуле создаются ТЗ для креаторов.
6. **Ревью брифов** — человек утверждает / отправляет на доработку / отклоняет.
7. **Продакшн и публикация** — креаторы снимают по ТЗ, ролики публикуются.
8. **Eval** — еженедельная оценка performance, выводы возвращаются в систему.

Этапы 2–6 и 8 выполняют ИИ-агенты на сервере. Между этапами стоят **ворота утверждения**: конвейер останавливается и ждёт решения человека. Это принципиально — система никогда не двигается дальше без явного «да» оператора.

Два железных принципа продукта, которые видны и в UI:

- **Evidence-first**: каждый паттерн, формула и бриф имеют ссылки на исходные данные (конкретные ролики, метрики). Цепочка происхождения: `source_url → pattern_id → formula_id → brief_id → prompt_version → reel_id → performance`.
- **insufficient_data — честный статус**: если данных мало, агент не выдумывает вывод, а возвращает `insufficient_data` со списком того, чего не хватает. В UI это нормальное состояние, а не ошибка.

## 2. Как устроена система (что уже есть, UI не строит это заново)

| Компонент | Роль |
|---|---|
| **n8n** (self-hosted) | Runtime: сбор raw-видео и performance-метрик. Управляется по HTTP API. |
| **ИИ-агенты** (Claude Agent SDK, Python) | Анализ, формулы, генерация и ревью брифов, eval. Запускаются headless на сервере: конвейер выполняет один запуск за раз, но внутри запуска ниши обрабатываются параллельно (пул из 2 воркеров; каждый прогон ниши пишет свои строки в CF Run Log). |
| **Google Sheets** | Операционное хранилище — источник правды. Вкладки: CF Raw TikTok, CF Raw Instagram, CF Creative Briefs, CF Published Reels, CF Performance, CF Prompt Versions, CF Run Log, CF Seeds. |
| **GitHub** | Версионируемое хранилище: промпты, формулы, proposals, решения. |
| **Python-пакет `cf`** (CLI) | Готовый слой доступа к данным: чтение/запись Sheets, лог запусков (CF Run Log), выставление статусов ревью, валидация, трассировка цепочки происхождения. Веб-приложение переиспользует этот пакет, а не пишет доступ к Sheets заново. |

Каждый запуск агента логируется в CF Run Log (вкладка Sheets): кто запускал, этап, статус (`success` / `insufficient_data` / `failed`), итог. Других статусов не бывает; в UI `failed` показывается как «Ошибка».

## 3. Пользователи

| Роль | Кто это | Что делает в UI |
|---|---|---|
| **Продюсер** (главный пользователь) | Нанимаемый сотрудник, **нетехнический** | Запускает конвейер целиком или по этапам, ведёт очередь брифов, утверждает/отклоняет, копирует ТЗ для передачи креаторам |
| **Админ** (владелец) | Тех-специалист | Всё то же + служебный срез: статусы интеграций, версии промптов, ошибки |

Следствие: язык интерфейса — русский, без технического жаргона для продюсера, статусы человеческим языком, действия крупные и однозначные.

## 4. Задача: веб-приложение, 4 экрана

Состав экранов утверждён, менять его не нужно.

### 4.1. Обзор конвейера (главный экран)
Этапы конвейера в виде цепочки со счётчиками объектов на каждом этапе и метками «ждёт действия». Оператор с одного взгляда видит, где конвейер остановился и что от него требуется. Клик по этапу ведёт к соответствующему экрану/списку.

### 4.2. Очередь брифов
Таблица брифов: дата / ниша / статус. Клик по строке открывает карточку брифа:

- полный текст ТЗ;
- цепочка происхождения (по какой формуле сгенерирован, из каких роликов выведены паттерны — ссылки);
- ворота утверждения: **утвердить / на доработку / отклонить** (при «на доработку» и «отклонить» — обязательный комментарий, он сохраняется в историю);
- производственные статусы после утверждения (передан креатору → снят → опубликован) — **новая функциональность, поля для неё в текущей системе нет**: сейчас после утверждения фиксируется только факт публикации (вкладка CF Published Reels). Прототип хранит эти статусы в своём слое; в контракт данных (раздел 8) они не входят;
- кнопка **«скопировать ТЗ»** — копирует текст брифа в буфер для отправки креатору.

Статусы ревью брифа: `pending` (ждёт ревью) → `approved` / `revised` (на доработку) / `rejected`.

### 4.3. Запуски
- Кнопка «запустить всё» (конвейер целиком, с остановками на воротах) и запуск отдельного этапа.
- Живой ход текущего запуска (какой этап, что происходит, сколько идёт).
- История запусков: дата, этап, кто запустил, статус, итог; статус `insufficient_data` показывается с перечнем недостающих данных.
- Одновременно выполняется только один запуск; попытка запустить второй — понятное сообщение, а не ошибка.

### 4.4. Служебный (только админ)
Статусы интеграций (Google Sheets, n8n — доступна/недоступна), активные версии промптов, последние ошибки запусков.

## 5. UX-принцип ворот утверждения (обязателен)

Перед каждым вопросом оператору интерфейс обязан показать:

1. **что сделано** — результат этапа;
2. **где прочитать подробности** — ссылка на документ/бриф, первым пунктом;
3. **последствия каждого варианта** выбора.

Никаких «утвердить?» без контекста.

## 6. Архитектура (утверждена, не пересматривать)

- **FastAPI + HTMX**, server-rendered HTML (Jinja2-шаблоны). **Никакого SPA / React / Vue** — интерактив только через HTMX-паттерны (частичные обновления, polling для живого хода запуска).
- Python — потому что переиспользуется существующий пакет `cf` (доступ к Sheets, лог запусков, статусы ревью).
- **Google Sheets — источник правды** по данным конвейера. Веб-приложение читает и пишет через существующий слой, ничего не дублирует.
- **SQLite** — только для очереди заданий (запуски агентов) и учёток пользователей. Не для данных конвейера.
- Агенты запускаются как фоновые задания на том же сервере (headless, Claude Agent SDK): конвейер — один запуск за раз, ниши внутри запуска идут параллельно (2 воркера); статус каждого прогона пишется в CF Run Log.
- n8n дёргается по HTTP API (запуск воркфлоу сбора).
- Авторизация: две роли (продюсер / админ), обычный логин-пароль, сессии.
- Хостинг: один VPS (приложение + агенты + n8n рядом).

Примечание 2026-07-22: реализованный MVP работает без SQLite и авторизации (см. `docs/superpowers/specs/2026-07-14-cf-dashboard-design.md`); блок выше — целевая картинка для будущих итераций.

## 7. Границы MVP

В MVP **не входит**: Telegram-уведомления, внешние (публичные) страницы брифов, редактор промптов в UI, аналитические дашборды. Промпты меняются только через git-процесс с ревью человека — UI их лишь показывает (версии).

Этот список — канонический; дизайн-бриф ([cf-ui-design-brief.md](cf-ui-design-brief.md)) ссылается сюда и своего списка не ведёт.

## 8. Что мокать

У тебя нет доступа к Google Sheets, пакету `cf` и n8n. Поэтому:

- построй слой доступа к данным как отдельный модуль с интерфейсом (репозиторий/сервис), а под ним — заглушку с реалистичными тестовыми данными на русском (брифы, запуски, статусы);
- реальная интеграция подключится позже заменой заглушки — структура данных из этого брифа (вкладки, статусы, цепочка происхождения) и есть контракт;
- запуск агента в прототипе — имитация (задание меняет статусы по таймеру). Очередь заданий строй как внутрипроцессную, но за отдельным интерфейсом: в проде это пул потоков внутри приложения (никакого SQLite и внешних брокеров там нет), и при реальной интеграции подменяется именно реализация за этим интерфейсом.
