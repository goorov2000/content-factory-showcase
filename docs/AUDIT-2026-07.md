## Оптимизация (эффективность)

Главный дефицитный ресурс — квота Google Sheets API; почти все точки в `sheets.py` и вызывающих. Подтверждённые находки:

- **`src/cf/dashboard/runner.py:152`** [CONF] — _raw_counts скачивает обе raw-вкладки целиком (включая тяжёлые raw_json/transcript_text) каждые 30 секунд только ради len(rows).

При ~2000 строк с колонкой raw_json (полный ответ Apify, килобайты на строку) каждый опрос — мегабайты трафика и 4 HTTP; выгрузка идёт 10-20 минут → десятки полных скачиваний и заметная доля квоты 60 read/min, хотя для подсчёта прироста хватило бы чтения одной колонки (ws.col_values) или ws.row_count из уже полученных метаданных.
- **`src/cf/sheets.py:96`** [CONF] — update_row_fields пишет каждую ячейку отдельным API-вызовом update_cell и перед этим читает всю вкладку get_all_records; update_rows_where (строка 117) — тот же паттерн на каждую совпавшую строку.

Сессия ревью из 20 брифов ≈ 180 HTTP → троттлинг 429 и паузы with_retry; batch_update/update одной строки-диапазона свёл бы запись к 1 вызову.

README на 76 КБ описывает как система работает, но нигде нет процедуры «машина умерла в среду — как в четверг выпускать брифы». При x5 темпа цена дня простоя вырастает впятеро.
- Предложение: docs/RUNBOOK.md на одну страницу: (1) чек-лист восстановления — клон репо, venv, восстановление secrets из менеджера паролей, cf backup/restore, запуск дашборда; (2) копии всех кредов (service account, n8n API key, Apify token, webhook-токен из п.4) в менеджере паролей, а не только на диске/в n8n; (3) полугодовой drill: восстановиться на чистой машине по документу и замерить время.
