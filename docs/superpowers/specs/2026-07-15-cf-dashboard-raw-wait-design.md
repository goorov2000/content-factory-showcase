# Дашборд CF: ожидание выгрузки raw + счётчики прокрута

Дата: 2026-07-15. Статус: дизайн согласован с оператором (варианты выбраны в диалоге).

## Проблема

1. Звено «Raw-ролики» дёргает n8n-вебхуки и мгновенно рапортует «успешно»: полный
   цикл тут же запускает «Контент-завод», пока Apify ещё выгружает строки в Sheets.
   Агенты анализируют неполный батч.
2. На карточке raw не видно, сколько роликов привёз текущий прокрут.
3. На карточке «Контент-завод» не видно, сколько внутренних операций (запусков
   агентов) совершило звено.

## Решения (выбраны оператором)

- Завершение raw определяем **наблюдением за таблицами** (вариант A): без правок
  n8n, без коллбэков. Побочный бонус — живой счётчик «+N за прокрут».
- Операции «Контент-завода» считаем **по CF Run Log** (вариант A): каждый агент
  уже пишет туда свой запуск; источник правды, агентов не трогаем.

## 1. Звено «Raw-ролики»: ожидание выгрузки и счётчик прокрута

Всё — внутри `StageRunner.run_sync` (ветка `kind == "n8n"`, только для звена
`raw`; `publish`/`stats` остаются fire-and-forget, как сейчас).

Механика:

1. До POST'а вебхуков: `base_tt = len(read_rows("raw_tiktok"))`,
   `base_ig = len(read_rows("raw_instagram"))`.
2. POST вебхуков — как сейчас (список URL поддерживается).
3. Цикл опроса каждые `poll_sec`: перечитать обе вкладки, `delta = Δtt + Δig`.
   Живой detail на карточке: `выгрузка: +37 (TikTok +25 · Instagram +12)` —
   partial `/partials/stages` уже перерисовывается каждые 2 с, UI не трогаем.
4. Завершение — одно правило (решение оператора: «если 3 минуты ничего не
   добавляется, значит всё готово»): прошло ≥ `stall_sec` с момента старта
   ожидания или последнего прироста → выгрузка завершена. Итоговый статус:
   прирост есть → **ok**; прирост нулевой → **warn** («сбор не привёз новых
   строк»), в Run Log — `insufficient_data`. Цикл опроса всегда конечен, потолок
   не нужен.
5. Итоговый detail (остаётся на карточке до следующего запуска):
   `+37 за прокрут · TikTok +25 · Instagram +12`.

Пороги в `cf.config.json`, оба опциональны (дефолты в коде):

```json
"dashboard": { "raw_wait": { "poll_sec": 30, "stall_sec": 180 } }
```

Блокировка следующего этапа:

- В полном цикле ничего дополнительно не нужно: `run_cycle_sync` последователен,
  а `run_sync("raw")` теперь возвращает управление только после конца выгрузки.
- Ручной ▶ на «Контент-заводе», пока raw в статусе `running`, получает отказ:
  `start("factory")` возвращает False и пишет в `cycle_note`
  «"Контент-завод" не запущен: raw ещё выгружается».

## 2. Звено «Контент-завод»: счётчик внутренних операций

1. До запуска промптов: `base = len(read_rows("run_log"))` (вкладка CF Run Log).
2. После каждого промпта (`/cf-analyze`, `/cf-generate-briefs`) и в финале:
   перечитать лог, взять строки `rows[base:]`, отбросить свои
   (`agent` начинается с `dashboard-`), сгруппировать по `agent`.
3. Detail: `операций 5 · анализ 2 · брифы 2 · ревью 1`. Между промптами detail
   обновляется, статус остаётся `running`; финальная строка — при `ok` и
   сохраняется до следующего запуска.

Словарь агентов → русские метки: `pattern-analyzer` → анализ,
`brief-generator` → брифы, `brief-reviewer` → ревью, `raw-batch-profiler` →
профилирование, `niche-classifier` → ниши, `formula-writer` → формула,
`eval-agent` → eval; незнакомые имена показываются как есть.

Допущение (осознанное, MVP): Run Log append-only; параллельные записи чужих
процессов за время звена попадут в счёт.

## 3. Реализация и тестируемость

- Все изменения — в `src/cf/dashboard/runner.py`; у `StageRunner` уже есть
  `sheets` и `config`.
- Для тестов у `StageRunner` появляются инжектируемые `sleep_fn` и `now_fn`
  (дефолты — `time.sleep` / `time.monotonic`).
- `_finish` учится не затирать наработанный detail (сейчас он пишет «успешно»):
  параметр `detail=None` → при None старое поведение.
- Ошибки: падение чтения Sheets в опросе идёт через существующий retry слоя;
  исчерпание ретраев — звено в `error` (как любой exception сейчас).

Тесты (fake sheets с последовательностью счётчиков, записывающий sleep,
управляемое время):

- завершение по 3 минутам тишины (после прироста и вовсе без него);
  warn при нулевом приросте;
- строки detail (живая и итоговая);
- в цикле factory стартует только после завершения ожидания raw
  (порядок вызовов run_command/http_post);
- отказ ручного ▶ factory при running raw + cycle_note;
- группировка операций по Run Log, исключение `dashboard-*`, незнакомый агент;
- пороги из config переопределяют дефолты.

## Вне охвата

- Ожидание завершения для `publish`/`stats` (по аналогии — позже, когда
  publish-воркфлоу вообще появится).
- Персистентность счётчиков между рестартами сервера (state в памяти — как весь
  runner).
- Точная привязка новых строк raw к конкретному запуску воркфлоу (считаем любой
  прирост за время ожидания).
