# CF на VPS: полная автономия без n8n — дизайн

Дата: 2026-07-22. Статус: **approved оператором 2026-07-23** вместе с планом реализации порта — [docs/plans/2026-07-23-collect-port.md](../../plans/2026-07-23-collect-port.md).

## Решение и мотивация

Наставник предложил отказаться от n8n и перенести сбор в Python-скрипт в репо.
Анализ 2026-07-21 (6 агентов: инвентаризация n8n, аудит Python-стороны, ops,
альтернативы, адвокат дьявола, критик полноты) подтвердил направление, а
брейншторминг зафиксировал целевую картину шире: **вся система работает
автономно на собственном VPS** (тот же сервер, где сейчас n8n; полный
админ-доступ есть), оператор только ревьюит и отвечает на уведомления.

Ключевой сдвиг против прежней рекомендации «Apify Schedules + GitHub Actions»:
гибрид был ответом на «нет своего сервера». Свой всегда-включённый VPS делает
его лишним — обычный cron на сервере проще, точнее и однороднее. Вариант
«оставить n8n планировщиком» отклонён: сохраняет два места правды,
push/pull-синхронизацию и задокументированные боли (невшитый coalesce P1.16,
ручные доводки графа в UI, дрейф inline-кода).

Зафиксированные вводные оператора:

- степень автономии — максимальная: система сама гоняет циклы, шлёт
  уведомления, оператор жмёт approve/reject;
- VPS свой, полный доступ (n8n.example.com);
- агенты — claude CLI на VPS по текущей подписке (не API-ключ);
- дашборд — публичный домен + HTTPS + пароль (доступ с любого устройства).

## 1. Целевая архитектура

На VPS:

- **cf-dashboard** — systemd-сервис, uvicorn на 127.0.0.1:8787;
- **Caddy** (reverse proxy) — `cf.example.com`, HTTPS через Let's Encrypt
  автоматом, доступ по паролю (basic auth на прокси; приложение не меняется);
  наружу торчит только Caddy, дашборд слушает localhost;
- **репо** — git-клон с GitHub (`<owner>/content-factory`); деплой:
  `git pull` + перезапуск сервиса одной командой (скрипт `deploy.sh`);
- **claude CLI** — авторизация подпиской; фан-аут работает как сейчас;
- **секреты** — `~/.cf/secrets/` на сервере (Apify-токен, service-account.json,
  Telegram-токен); n8n-api-key и webhook-token устаревают после сноса n8n;
- **systemd-таймеры** — все расписания (см. §3).

Ноутбук (Windows) — только разработка: git push → деплой на сервере. Я.Диск-синк
перестаёт касаться рантайма (известные проблемы .git/os.replace остаются только
дев-неудобством).

## 2. Порт сбора — `src/cf/collect`

Новый пакет: `tiktok.py`, `instagram.py`, `snowball.py`, `performance.py` +
общие `gate.py`, `normalize.py`, `coalesce.py`, `subtitles.py`, `apify.py`.
CLI: `cf collect tiktok|instagram|snowball|performance`.

- Логика переписывается **1:1 с `n8n/*/code/*.js`** (уже вынесена из графов и
  покрыта ~1400 строками JS-тестов); тесты переезжают в pytest как критерий
  готовности порта: инварианты потерь (`batches_failed` по уникальным
  `batch_index`, громкий fail при «0 рядов и ≥1 упавший батч», двухточечный
  учёт Instagram), строгий детект error-item (есть `error` И нет id/url),
  парсер субтитров VTT/JSON3/plain, дедуп seed, нишевый фильтр IG, грамматика
  `source_query` (hashtag:/query:/snowball:/unknown — контракт /cf-tune-sources).
- **Apify-клиент**: асинхронный паттерн start + poll (вместо
  run-sync-get-dataset-items) — снимает лимит 300 с и позволяет параллельные
  батчи (в n8n HTTP-нода гоняла их последовательно, worst-case ~36 мин);
  ретраи поверх существующего `retry.py`; изоляция сбоя батча сохраняется.
  Терминальные статусы (SUCCEEDED/FAILED/ABORTED/TIMED-OUT) и таймаут
  поллинга — новые режимы отказа, покрываются отдельными тестами.
- **Sheets-upsert по `raw_id`** поверх `sheets.py` (read keys → update/append;
  в gspread нативного upsert нет) + **coalesce P1.16 сразу**: для существующих
  `raw_id` сохранять `transcript_text` (если новый пуст), `source_query`,
  `collected_at`; остальные колонки — свежие. Обязателен до первого боевого
  snowball (пишет в тот же лист CF Raw TikTok). Заголовки листов не меняем —
  `column_aliases` остаются как есть.
- Сводки гейтов/потерь идут в лог процесса и в лист CF Run Log через
  `runlog.log_run` (улучшение против запертых execution-логов n8n).
- **Дашборд**: звено raw (kind был «n8n») запускает subprocess
  `python -m cf collect ...` через существующий `run_command` (паттерн звена
  factory), под теми же ProcessLock/mutex raw↔factory. Удаляются: `_wait_for_raw`
  (поллинг count_rows), `_default_post`/`_webhook_token` и весь контур X-CF-Token.
- **CF 04 Performance**: выгружен с живого n8n 2026-07-22
  (`n8n/cf04-performance/`, id DCLSn9Gm7pz4rksd, коммит 40bf69b). Факты:
  cron-триггера НЕТ (только Manual Start + вебхук `cf-stats` от дашборда —
  «ежедневный CF 04» из доков был намерением, не фактом); конвейер простой —
  Read CF Published Reels → Build Apify Metric Requests → один Apify-вызов →
  Normalize Performance Rows → Write CF Performance (~180 строк JS). Порт как
  `cf collect performance` (контракт: строки несут `brief_id`, `measured_at`,
  `reel_id`, `er`; join по `post_url` из CF Published Reels).
- `cf apply-sources` перенацеливается: SOURCES-списки переезжают из
  `Build-*.js` в реестр `sources/` (см. §2.1), proposal-цикл завершается
  git-коммитом (шаг `cf push-n8n` исчезает).

## 2.1. Умные источники — exploration-контур

Порт вскрывает главный побочный выигрыш: списки «что скрейпим» перестают быть
замурованными в JS-нодах n8n и становятся данными в репо, которые агентская
система читает и меняет. Решение оператора (2026-07-22): **авто-эксплорейшн в
рамках квоты, изменения постоянных списков — через proposal с approve**.

- **Реестр `sources/`** (`tiktok.json`, `instagram.json`): записи
  `{query, kind: hashtag|search, niche, status: active|candidate|paused|retired,
  origin: operator|tuner|harvest|discovery, added_at}`. Сбор читает active +
  exploration-квоту. Скоринг — существующий `source-stats` по атрибуции
  `source_query` (грамматика не меняется).
- **Exploration-квота**: ежедневный сбор добавляет 1 батч (≤4 источника)
  кандидатов на платформу рядом с проверенными. Детерминированно, без LLM в
  ежедневном пути (философия проекта: runtime — код, интеллект — в proposals).
- **Подпитка кандидатов**: (а) *harvest* — хэштеги из капшенов топ-строк raw
  (высокий ER / прошли гейт), детерминированная выжимка после сбора;
  (б) *Apify-discovery* — у Instagram уже есть, обобщается в общий шаг
  (TikTok — опционально, позже); (в) *агент* /cf-tune-sources.
- **Взросление/отсев**: кандидат с ≥2 прогонами — детерминированные пороги:
  ниже порога yield → retired (система сама, git-коммит раннера + строка в
  Telegram-отчёте); выше → попадает в proposal на перевод в active. Точные
  пороги — в плане реализации.
- **Гейт оператора**: add/pause/retire в active-списках — только через
  proposal → approve в дашборде (Лаборатория), тот же паттерн, что у формул.
  /cf-tune-sources гоняется еженедельно на сервере автоматически (таймер §3)
  и готовит evidence-backed proposal: какой тег дал сколько строк через гейт,
  какой ER у контента с него, кого из кандидатов повысить.
- **Связь с проектом**: ниши — из `target_niches`; при появлении новой ниши
  (/cf-classify-niche) агент предлагает стартовый набор источников; winners
  approved-формул подпитывают и snowball (уже есть), и harvest.

## 3. Расписания и автономный цикл

systemd-таймеры (Persistent=true — догон после ребута сервера):

| Время | Задание |
| --- | --- |
| 07:00 ежедневно | бэкап Sheets |
| вс 07:10 | архив/ретенция |
| 07:30 ежедневно | утренний цикл: POST localhost:8787/cycle/run (фан-аут + formula-guard + perf-проверка) |
| 08:00 ежедневно | `cf collect tiktok` |
| 08:20 ежедневно | `cf collect instagram` |
| вс 09:00 | `cf collect snowball` |
| 08:40 ежедневно | `cf collect performance` (новое расписание: в n8n его не было — метрики собирались только кнопкой) |
| вс 10:00 | source-tuner: агент готовит proposal по источникам (§2.1) |

Таймеры сбора зовут CLI напрямую (`python -m cf collect ...`), а не через
дашборд: межпроцессные локи (`lock.py`, ProcessLock) уже исключают гонку с
запуском той же стадии из дашборда, а CF Run Log пишется из самого пайплайна
через `runlog.log_run` — путь записи один для обоих способов запуска.

Дашборд всегда запущен на том же хосте — проблема «POST /cycle/run некуда
слать» (незаведённый schtasks 07:30 из RUNBOOK §3) исчезает. Windows-задания
CF Morning Cycle/Backup/Archive на ноутбуке упраздняются.

## 4. Агенты на VPS

claude CLI ставится на сервер, авторизуется подпиской оператора
(долгоживущая авторизация; ротация логина — операторская процедура в RUNBOOK).
Фан-аут (workers=2) без изменений логики. Git-коммиты раннера и кнопок решений
идут на сервере (deploy-ключ GitHub с правом push). Ручные ритуалы
(/cf-eval, /cf-tune-sources, /cf-review-brief) — с ноутбука по git-синку
или по SSH на сервере.

## 5. Уведомления — Telegram

Модуль `src/cf/notify.py` (HTTP к Bot API; token и chat_id в секретах),
замена пустого `notify_url`. События: сбор упал / 0 строк
(insufficient_data), N pending-брифов после цикла, formula-guard поставил
формулу на паузу, готов proposal по источникам / сводка exploration
(кандидаты повышены/отсеяны, §2.1), heartbeat «ежедневный таймер не
отработал». Деградация
мягкая: нет токена — warning в лог, конвейер не блокируется.

## 6. Порядок миграции (n8n живёт до конца приёмки)

1. **С живого n8n** — выполнено 2026-07-22, кроме токена: список снят
   (ровно 4 воркфлоу — CF 01 ×2, CF 01b, CF 04; все теперь версионированы;
   легаси CF 03 отсутствует); CF 04 выгружен (коммит 40bf69b, вебхук
   `cf-stats` — внутри него); credentials перечислены (4 шт., метаданные).
   Проверено: API n8n секреты credential'ов не отдаёт — **Apify-токен берётся
   только из console.apify.com** (Settings → API tokens; скопировать или
   выпустить новый) → положить в `~/.cf/secrets/apify-token.txt` и менеджер
   паролей. Это единственный оставшийся операторский шаг этапа.
2. Порт `src/cf/collect` + pytest на ноутбуке (критерий — зелёный порт всех
   JS-инвариантов).
3. Развёртывание на VPS рядом с живым n8n: git-клон, systemd-сервис
   дашборда, Caddy + домен + пароль, claude CLI, секреты, таймеры (выключены).
4. **Приёмка**: параллельный прогон — Python и n8n собирают одни источники,
   diff строк листа; тест с искусственно битым батчем (несуществующий
   хэштег/таймаут) — остальные батчи доезжают, потери в CF Run Log; особое
   внимание Instagram (контракт reel-scraper: reel-URL в поле `username`,
   формы ошибок акторов известны только по живым ранам).
5. Переключение: таймеры Python включаются, расписания n8n выключаются;
   неделя наблюдения (n8n стоит выключенный, но не снесён).
6. Снос n8n; чистка репо: `n8napi.py`, `n8nsync.py`, `cmd_pull_n8n`/
   `cmd_push_n8n`, `check_n8n` в health (заменить чеком Apify), блок `n8n` и
   `dashboard.workflows` в cf.config.json, `n8n/` (после порта тестов),
   `test_n8napi.py`/`test_n8nsync.py`; правка RUNBOOK и docs/n8n-integration.md
   (архив). Дашборд на ноутбуке остаётся работать до шага 5 как фолбэк.

## 7. Тестирование

- pytest-порт всех JS-тестов (спецификация порта, §2).
- Юнит: apify-клиент (start/poll/терминальные статусы/таймауты) на моках;
  sheets-upsert + coalesce на фейковом листе.
- Smoke: `cf collect tiktok --dry-run` (1 батч, без записи в боевой лист).
- Приёмочные критерии — §6 п.4; далее недельное наблюдение.

## 8. Вне скоупа

Авто-постинг рилсов, Docker-изация, отдельная очередь задач, уход с Google
Sheets, кука-логин дашборда (basic auth достаточно; апгрейд — отдельной
задачей при необходимости).

## Открытые вопросы

- Ресурсы VPS (RAM/CPU) под фан-аут claude CLI — проверить на шаге 3;
  при нехватке поднять тариф VPS.

Примечание о секретах: репозитории приватные, продукт пока внутренний
(решение оператора 2026-07-22 — ротация ключей не блокер миграции). Секреты
всё равно живут вне репо (`~/.cf/secrets` / GitHub Secrets не используется);
при выходе в b2b гигиена секретов станет обязательной — архитектура уже
ей соответствует.
