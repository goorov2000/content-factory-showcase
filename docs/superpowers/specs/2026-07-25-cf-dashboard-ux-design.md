## Проблема

Дашборд функционально силён и на десктопе выглядит хорошо, но:

1. **Говорит языком системы, а не продюсера.** Интерфейс подписан внутренними терминами (`ниша`, `формула`, `паттерн`, `бриф`, `eval`, `RAW`, `ER`, `фан-аут`), именами инструментов (`N8N`, `CLAUDE CODE`), слагами агентов и названиями Google-таблиц. Новый SMM-продюсер (второй пользователь по [BUSINESS-CONTEXT.md](../../BUSINESS-CONTEXT.md)) не понимает, что перед ним и где его зона ответственности.
2. **Не адаптивен вообще.** В `style.css` нет ни одного layout-медиазапроса; сайдбар не сворачивается, KPI-карточки и таблицы крошатся на мобильном — с телефона сервис непригоден.
3. **Долг дизайн-системы и порога доступности:** десятки инлайн-стилей вместо классов, необъявленный шрифт, `.empty-state` рисует логотип под ошибками, нет label/aria/skip-link.

## Принципы (рамки работ)

- **Это доводка, а не редизайн.** Десктопный визуал хорош — его сохраняем; работаем над языком, адаптивностью и долгом ДС.
- **Аудитория — новый продюсер.** Приоритет: ясность → навигация → визуал (решение оператора от 2026-07-25).
- **Прятать, не удалять.** Тех-детали (слаги агентов, дампы) полезны владельцу как диагностика — уводим их под `<details>`/в «Запуски», но не выбрасываем.
- **Прод-осторожность.** Правки — в шаблонах (`src/cf/dashboard/templates/`) и одном `style.css`; логику раннера/данных не трогаем. Деплой на VPS — как обычно (git → pull → рестарт `cf-dashboard`).
- **Каждая фаза — с тестами и коммитом.** Прогонять `pytest` (сейчас 1156 зелёных); менять/добавлять `tests/test_dashboard_*`, `tests/test_lab_*`. После адаптивной фазы — переснять скриншоты скиллом `web-design-reviewer` для контроля.
- **Промпты не трогаем** (правило №3 CLAUDE.md): UI-copy в шаблонах — можно; тексты в `prompts/**` — только через proposal.

## §1. Что НЕ входит

- Редизайн визуального языка, смена палитры/логотипа.
- Массовые действия/фильтры в очередях (это отдельная задача про скорость решений — оператор её сейчас не приоритизировал).
- Функциональные изменения конвейера, данных, раннера.

## §2. Языковой слой — фундамент (нужно согласование оператора)

Единый словарь «система → пользователь», применяемый сквозь все шаблоны. **Утверждён оператором 2026-07-25** (опрос, разбор по одному термину):

| Система | Пользователь (утверждено) |
|---|---|
| бриф / скрипт / рил / reels | **сценарий**; опубликованное — **ролик** |
| ниша | **тема** |
| формула | **рецепт ролика** |
| паттерн | **приём** |
| RAW / raw-видео / Raw-ролики | **собранные ролики** |
| ER | **вовлечённость** (%, tooltip-расшифровка при первом показе) |
| eval | **Eval-петля** (термин оставлен по решению оператора) |
| звено (шаг конвейера) | **этап** |
| фан-аут / approved-индекс / prompt version / пути к конфигам | **убрать из вида продюсера** |
| статусы approved/reject/revise/recommend/insufficient_data | **утверждено / отклонить / доработать / рекомендовать / данных мало** |
| actor-плитки конвейера | **имена инструментов сохраняем**, но **N8N → Apify** (см. ниже) |

**Actor-плитки (нюанс, решение оператора):** имена инструментов оставляем (не роли), но `N8N → Apify`. Это ещё и фактическая правка: сбор (raw/статистика) с 2026-07-24 идёт через Apify, n8n списан ([cf-audit](../../../CLAUDE.md)). Исключение — плитка публикации `ПРОДЮСЕР · N8N`: звено `publish` технически всё ещё на n8n-вебхуке (этап 6 не сделан) — там либо оставить `N8N`, либо уточнить у оператора при реализации.

Реализация словаря: единая точка, чтобы не рассыпать по 9 шаблонам —
- **где статично** (заголовки, eyebrow, подписи колонок): правим текст в шаблонах напрямую;
- **где значения из данных** (статусы, actor, agent-слаги, платформы): один Jinja-фильтр/словарь (напр. `templates`-глобал `LABELS` или фильтр `humanize`), подключаемый в `app.py`, чтобы перевод был в одном месте и переиспользовался. Числа (просмотры, ER) — единый фильтр форматирования (`fmt_views`, `fmt_pct`) вместо трёх форматов.

Правило-инвариант: **одна сущность — одно слово** (сценарий; ролик; тема). Тест на регресс: grep по шаблонам не должен находить `reels`, сырой `0.` в ER-колонках, `approved` латиницей в русских строках.

## §6. Оценка объёма

Фазы 1–3 — преимущественно copy + один слой фильтров: быстро, низкий риск, наибольший эффект. Фаза 4 — средне (один `style.css` + бургер). Фазы 5–6 — механические, разово. Реалистично разбить на 3 подхода: (1) язык+навигация+обзор, (2) ясность по разделам, (3) адаптивность+ДС+a11y. Каждый подход — свой набор тестов и коммит.
