# Конвейер CF: вертикальная лента, счётчики за прогон, симулированный прогресс — дизайн

Дата: 2026-07-25. Статус: дизайн согласован с оператором (опрос). Часть Фазы 2 UX-доводки ([2026-07-25-cf-dashboard-ux-design.md](2026-07-25-cf-dashboard-ux-design.md)).

## Проблема (из заметки оператора)

1. Плитки конвейера показывают числа **за период** (окно дней из Sheets), а нужно — **за текущий прогон**; в покое (idle) — числа **прошлого прогона**; при старте прогона — обнулять и считать заново.
2. Плитка при выполнении просто горит синим — нет ощущения прогресса. Нужна **полоска загрузки**, чтобы примерно понимать, скоро ли завершится этап.
3. Перекос: 5 плиток, вес смещён вправо (одобрение/съёмка/статистика). Самая ценная часть — путь **от собранного ролика до сценария** — схлопнута в один непрозрачный «Контент-завод». Продюсер не видит, какой агент сейчас работает, не может открыть и понять цепочку.

## Решения (согласованы, опрос 2026-07-25)

- **Форма:** вертикальная лента (шаг = строка). ✔
- **Обнуление за прогон:** только производящие шаги (Сбор→Ревью) обнуляются и считаются за прогон; правые (Одобрение/Съёмка/Статистика) — живой бэклог, не обнуляются. ✔
- **Прогресс:** детерминированный там, где есть реальные `done/total`; иначе — **симулированный детерминированно-выглядящий** бар (проценты по времени против медианы), плавно к ~92%, добивка до 100% по факту завершения. ✔

## 1. Цепочка агентов (8 шагов) — раскрытие «Контент-завода»

Первые 5 шагов сейчас скрыты в одной плитке; раннер уже проходит их по шагам в `run_fanout_sync`. Термины — из утверждённого словаря (§2 UX-спеки).

| # | Шаг (UI) | Агент/механика | Счёт за прогон | Прогресс |
|---|---|---|---|---|
| 1 | Сбор | Apify (`collect tiktok/instagram`) | собрано роликов (+N) | реальный: 2 платформы / по батчам |
| 2 | Разметка тем | niche-classifier ×2 вкладки | размечено роликов · тем | реальный: 0/2..2/2 |
| 3 | **Анализ тем** | niche-pipeline (профайл+приёмы+рецепты) | тем разобрано `done/total` · рецептов N | **реальный `done/total`** (раннер уже считает) |
| 4 | Сценарии | brief-generator | создано сценариев | симулированный (медиана) |
| 5 | Ревью | brief-reviewer | проверено · рекомендовано | симулированный (медиана) |
| — | _(страховка формул)_ | formula-guard/perf | — | служебное, не показывать плиткой |
| 6 | Одобрение | **вы** | ждут решения (бэклог) | — |
| 7 | Съёмка и публикация | вы (+ публикация) | роликов вышло (бэклог) | — |
| 8 | Статистика | Apify (`collect performance`) | ждут данных (бэклог) | реальный, короткий |

Между шагом 5 и 6 — визуальный разделитель «дальше — ручные этапы (вы)».

## 2. Модель данных раннера (per-run)

Раннер ведёт per-run состояние по шагам:

```
run_progress = {
  <step>: {
    status: idle|running|done|warn|error,
    count: <int>,        # за текущий прогон (обнуляется на старте)
    last_count: <int>,   # прошлый прогон (показывается в idle)
    done: <int|null>,    # реальные шаги (напр. ниши), либо null
    total: <int|null>,
    started_at: <mono|null>,   # для симулированного прогресса
    eta_median: <sec|null>,    # медиана длительности агента из Run Log
  }
}
```

- **Старт прогона/звена:** производящим шагам `count←0`, `status←…`, `started_at←now`; `last_count` сохраняется (для idle).
- **По ходу:** инкремент `count`/`done` по мере завершения под-шагов; `status` шага меняется idle→running→done.
- **Idle:** UI показывает `last_count` (или `count`, если прогон не завершён).
- **Персист:** снапшот `run_progress` на диск (как «Отчёты звеньев» — `agent-runtime/…`), чтобы idle-числа и «прошлый прогон» пережили рестарт дашборда.
- **Downstream (6–8):** не из `run_progress`, а живой бэклог из `overview_metrics` (как сейчас) — «сколько ждёт прямо сейчас».

**Медианы длительностей** для симулированного ETA — из CF Run Log (`started_at`/`completed_at` по агенту): считаем медиану последних N успешных запусков агента шага. Нет истории → фиксированный дефолт-профиль (напр. 90с) и более пологая кривая.

## 3. Прогресс-бар: реальный и симулированный

- **Реальный** (шаги 1–3, 8): `width = done/total`. Для «Анализа тем» раннер уже отдаёт `done/total` ниш — это главный длинный шаг, и он получает честную полоску.
- **Симулированный** (шаги 4–5): сервер отдаёт `started_at` и `eta_median`; ширина = асимптотическая функция времени, никогда не достигает 100% сама:
  `p = 1 − exp(−elapsed / eta_median)`, кэп на ~0.92; при `status=done` → мгновенно 1.0.
  Это «детерминированно-выглядящий» бар: плавно ползёт, не врёт обратным отсчётом, честно добивается по факту.
- **Плавность между опросами:** HTMX перерисовывает `#stages` раз в 2с — этого мало для гладкости. Клиентский тикер (~200мс) сам интерполирует ширину бегущего шага по `data-started`/`data-median`/`data-frac` на элементе; опрос лишь обновляет базовые данные (флип done/total, завершение). CSS `transition: width` сглаживает скачки при свопе.
- Уважать `prefers-reduced-motion` (в CSS уже есть ветка): при reduce — без анимации тикера, только дискретные обновления.

## 4. UI — вертикальная лента

Строка шага: `[иконка-статус] Название · агент · [полоска] · счёт-за-прогон · [открыть →]`.
- Иконки статуса: `●` done / `◐` running / `○` waiting / `!` warn/error.
- «Открыть →» — ссылка в релевантный раздел (Анализ тем → Аналитика; Сценарии/Ревью → Сценарии; Одобрение → Сценарии(очередь); и т.д.).
- Разделитель после шага 5: «дальше — ручные этапы».
- Кнопка «▶ полный цикл» и запуск отдельного шага — сохранить (как сейчас у плиток с раннером).
- Адаптивность бесплатно: вертикаль стекается на мобильном (закрывает и часть Фазы 4).

## 5. Приёмка и тесты

- В покое лента показывает числа прошлого прогона; старт «полного цикла»/шага обнуляет производящие счётчики, downstream остаётся живым бэклогом.
- «Анализ тем» показывает реальный `done/total` по нишам; «Сценарии»/«Ревью» — симулированный бар, добивающийся до 100% по завершению; ни один бар не достигает 100% раньше факта.
- Медиана берётся из Run Log; нет истории → дефолт-кривая без ошибок.
- Тесты: `test_dashboard_runner` — per-run reset/last_count/persist; расчёт прогресса (реальный и симулированный, кэп <1.0 до завершения); `test_data`/`test_dashboard_routes` — downstream остаётся периодным/бэклогом; рендер ленты (`test_lab`-стиля для stages).

## 6. Открытые мелочи

- Плитка публикации `ПРОДЮСЕР · N8N`: звено `publish` технически на n8n (этап 6). По умолчанию оставить `N8N`, если оператор не скажет иначе (сбор — `Apify`, это уже правка).
- «Открыть →» для шага «Сбор» → Референсы (бывш. Источники); «Разметка тем» → Аналитика (темы).

## 7. Прогресс v2 — факты как якоря, кривая как интерполяция (правка оператора 2026-07-25)

**Что не устроило в v1 (проверено на живом прогоне):** полоска шага «Сбор» — это
`done/total` по **платформам** (2 штуки), а `done` растёт только когда платформа
дошла до конца. Оператор видел две минуты нуля, затем мгновенный скачок на 50%.
Причина глубже разметки: `_run3` забирает вывод подпроцесса целиком в конце
(`communicate`), а `cf collect` печатает одну строку-сводку — внутри платформы
прогресс просто не наблюдаем. Требование оператора: **показывать реальную ситуацию**,
но двигаться по «психологически честной» кривой (быстрый старт, замедление к концу,
без скачков и без движения назад), и подписывать текущую фазу словами.

### 7.1 Модель

Три слоя, каждый со своей ответственностью:

1. **Якоря (факт).** Раннер знает завершённые единицы работы: платформы (Сбор),
   вкладки (Разметка), темы (Анализ). Внутри Сбора добавляется настоящая
   гранулярность — **батчи Apify** (обычно 8 на платформу): их считает сам
   `cf collect` и печатает маркерами в stdout, раннер читает stdout **потоково**.
2. **Фазы с весами.** Единица работы делится на фазы, вес = сколько полоски она
   занимает. Это и есть «быстрые первые 15–25%»: подготовка реально закончена, значит
   бар честно стоит на её весе, а не на нуле.
3. **Кривая внутри фазы.** Там, где факта нет (claude внутри темы, гейт, запись),
   доля внутри фазы = `1 − exp(−t/τ)`, τ — медиана из Run Log: быстрый старт,
   замедление к концу, кэп 0.95 сегмента. Сервер отдаёт клиенту `frac` (текущее),
   `ceil` (докуда можно доехать без новых фактов) и `τ`; клиентский тикер (200 мс)
   асимптотически приближает `frac → ceil`. Итог монотонен по построению: следующий
   якорь всегда выше достижимого потолка предыдущего сегмента.

Инварианты: полоска **не идёт назад** (`display = max(prev, computed)`), **не
превышает 0.95** до подтверждения завершения, и доезжает до 100% только по факту
(`status=done`), плавно — CSS-переход 600 мс.

### 7.2 Фазы по шагам (специфика проекта, не абстрактные «обработка/завершение»)

Шаг «Сбор», внутри каждой платформы (TikTok, Instagram):

| Фаза | Вес | Что реально произошло | Подпись |
|---|---|---|---|
| `prepare` | 0.15 | реестр источников прочитан, батчи собраны — известно N | «Готовим источники» |
| `fetch` | 0.60 | k из N батчей Apify вернулись (**реальный якорь**) | «Собираем ролики · k/N батчей» |
| `gate` | 0.15 | гейт отфильтровал/дедуплицировал строки | «Отбираем годные» |
| `write` | 0.10 | upsert в Sheets + строка в Run Log | «Записываем в базу» |

Шаги «Разметка тем» / «Анализ тем»: якорь — вкладка/тема `done/total`, внутри единицы
кривая по времени, подпись — «Тема 2 из 5: мужские образы».
Шаги «Сценарии» / «Ревью»: якорей нет (один вызов claude), чистая кривая, подписи
«Пишем сценарии» / «Проверяем сценарии».

### 7.3 Что доработать в коде

- `cf.collect.apify.run_batches(..., on_done=cb)` — колбэк на каждый готовый батч.
- `cf collect tiktok|instagram|performance` печатает стабильные маркеры
  `CF_PROGRESS phase=… done=… total=…` (в отчёты звена маркеры не попадают).
- `runner._run3` читает stdout построчно (stderr — отдельным потоком, дедлайн 1800 с
  сохранён) и отдаёт строки колбэку; CLI-звено парсит маркеры в `run_progress`.
- `progress.py`: веса фаз, `bar_fraction` с фазами, `phase_label`, `ceiling`.
- Лента: рядом с полоской — подпись фазы, «идёт 2:14» и процент; у иконки статуса —
  подпись (оператор спросил «что это вообще за элемент» — значок сам себя не объясняет).

### 7.4 Приёмка

- На реальном прогоне «Сбор» едет непрерывно: prepare → 8 батчей → gate → write по
  каждой платформе, без прыжка 0 → 50%.
- Ни одна полоска не выше 95% до подтверждения; после подтверждения — плавно 100%.
- Полоска никогда не уменьшается (в т.ч. на htmx-свопе и при перезагрузке страницы).
- Рядом с баром всегда написано, что именно сейчас происходит, и сколько идёт.

### 7.5 Правка: кривую ведёт клиент (жалоба оператора на живом прогоне 2026-07-25)

**Симптом:** «полоска скачет каждые 2–3 секунды, её как будто отталкивает назад».
Воспроизведено покадрово: в фазе с якорями (`fetch`/`reels`) сервер между батчами
честно стоит на месте, а `#stages` подменяется htmx каждые 2 с — в свежей разметке
инлайновая ширина равна серверному якорю, то есть **ниже уже показанной**. Кадр с
якорем успевал попасть на экран (тикер поправлял ширину лишь на следующем шаге, до
200 мс спустя), и бар отскакивал назад; вдобавок клиент начинал кривую заново от
якоря на каждом свопе — за 2 с он успевал пройти лишь её начало, и между фактами
полоска почти не двигалась (колебалась в пределах ~1 п.п.).

Разделение ответственности уточняется так: **сервер даёт только якоря, кривую между
ними ведёт клиент.**

- `data-frac` — якорь, это **пол**, а не точка перезапуска: свой отсчёт клиент не
  сбрасывает, пока сервер не прислал новый якорь.
- `data-ceil` — **следующий якорь**, а не конец фазы: в фазе с фактами это
  `(k+1)/N` батчей (кривая не имеет права убежать дальше ближайшей правды), в фазе
  без фактов — предел её же серверной кривой (`floor + weight·SEGMENT_CAP`), иначе
  клиент целится выше, чем сервер вообще способен показать.
- `data-tau` — время до этой точки: в фазе с якорями τ делится на число батчей
  (отрезок кривой — один батч, а не вся фаза).
- `data-run` — метка запуска шага (`started_at` раннера). Сменилась — полоска новая,
  накопленная ширина забывается. Страховка на случай отсутствия метки: якорь,
  провалившийся ниже показанного больше чем на четверть полоски, тоже считается
  новой полоской.
- Ширина проставляется прямо в `htmx:afterSwap` — синхронно, до отрисовки кадра.

Приёмка (покадровая, `requestAnimationFrame`): за 55 с в фазе `fetch` — ноль
движений назад, бар непрерывно подходит к каждому следующему якорю снизу; до правки
на том же сценарии — 14 откатов за 30 с, ровно по одному на своп htmx.

### 7.6 Счёт в единицах результата, таймер после финиша, ETA из замеров

Три правки оператора одним заходом (25.07, после полного цикла).

**1. Считаем добычу, а не единицы обхода.** «2/2 платформ», «2/2 вкладок» — это как
работу нарезала машина; оператору нужно, что получилось:

| Шаг | Было | Стало |
|---|---|---|
| Сбор | `2/2 платформ` | `118 роликов · 24 новых` (`rows`/`new` в маркере после upsert) |
| Разметка тем | `2/2 вкладок` | `107 роликов размечено · 12 без темы` (строки без `niche` до и после шага) |
| Анализ тем | `0/0 тем` | `1 из 3 тем · 2 рецепта`, пустая очередь → `тем в очереди нет` |
| Сценарии | `идёт…` | `2 сценария` (лист брифов до и после шага) |
| Ревью | `идёт…` | `2 проверено` (ушло из очереди `pending`) |

Числа считает раннер, а не парсер прозы: агенты отчитываются текстом, и счётчик из
текста — это ложь при первой же смене формулировки. Нет данных (Sheets недоступен,
шаг ещё не дал результата) → показываем состояние шага, а не ноль: «ничего не нашли»
и «ещё не искали» — разные ответы. Числительные склоняются (`plural_ru`), включая
downstream-бэклог: «1 ждёт решения», а не «1 ждут решения».

**2. Таймер остаётся после финиша.** `duration` засекается в момент перехода шага в
терминальный статус (в т.ч. у сорвавшегося — «сколько прожил до сбоя» тоже ответ) и
показывается под полоской: «шёл 18:02». Переживает рестарт вместе со снимком
прогресса.

**3. ETA — из собственных замеров.** Медиана из Run Log не работает: `cf log-run`
пишет `started_at = completed_at`, поэтому все 211 строк лога имеют нулевую
длительность, медиана = 0 и раннер молча падал на `DEFAULT_ETA_SEC = 90`. Отсюда
«шаг обещал полторы минуты, а шёл 18»: 90 секунд — это дефолт «истории нет», а не
замер. Теперь порядок источников: собственные замеры раннера (последние 5, файл
`agent-runtime/reports/step-durations.json`) → медиана Run Log → дефолт. Замеряется
только `done`: длительность сбоя — не оценка работы.

Долг: `cf log-run --started-at` и передача старта из агентов — тогда реальные
длительности появятся и в Run Log (нужны eval и «Истории задач»). Это правка
промптов агентов, поэтому только через proposal (железное правило №3).
