# UTM-контур: спецификация

Статус: ready-for-agent. Дата: 2026-07-30.
Бриф-идея: `docs/plans/2026-07-30-utm-contour/brief.md`.
Решения сняты грилем с владельца 30.07 (7 вопросов, см. «Решения гриля» ниже).

## Problem Statement

Заводу нечем привязать ролики к деньгам. С 30.07 действует схема оплаты
продюсера «ставка за уникальный переход по UTM + процент с подтверждённых
продаж» (значения ставок — блок `payout` конфига; в витринной копии не
публикуются) — без счётчика каждая выплата превращается в спор, а спор о
деньгах разрушает сотрудничество. Параллельно eval-петля судит формулы по
просмотрам и ER — прокси, который «кормит нахлебника, не умеющего вести на
сайт». Unit-экономика не считается вообще. Дедлайн: к первой оплачиваемой
неделе продюсера счётчик обязан показывать цифры, которым верят обе стороны.

## Решения гриля (30.07, владелец)

1. **Сайт** — конструктор Яндекс.КИТ на `jelapeche.com`, работает, готов к
   продажам. Позже возможен переезд на самописный сайт — контур обязан
   пережить переезд без переделки (адаптер источника заказов).
2. **Метрика** — счётчик на сайте стоит; владелец заведёт OAuth-токен для
   API. Правила подсчёта в оффере уже сформулированы «по UTM в Метрике».
3. **Заказы** — «своё решение», интеграция с КИТом сразу. Ресёрч: публичного
   API у КИТа нет (обещан «скоро»), поэтому интеграция идёт через яндексовский
   стек: e-commerce события КИТ → Метрика → наш сборщик. Свой реестр заказов
   в CF — источник истины по статусам; будущий API КИТа или вебхук своего
   сайта подключаются как ещё один источник строк того же реестра.
4. **Деньги считаются по аккаунтам** — выплата опирается только на
   неоспоримое: уникальные посетители по UTM-ссылке аккаунта из Метрики.
5. **По-роликовая статистика — обязательна как аналитика**: точная там, где
   в ссылке есть метка ролика, оценочная (помечена «оценка») — везде ещё.
   В расчётный лист продюсера оценка не входит.
6. **Регистрация публикаций** — кнопкой в пульте (URL + аккаунт) в очереди
   съёмки. Автоскрейп своих аккаунтов — следующий этап, вне скоупа.
7. **Прозрачность двоим** — страница «Деньги» в пульте (у продюсера будет
   пароль пульта на `cf.example.com`) + экспорт расчётного листа в
   markdown для пересылки. Во всех отчётах — сноска «контур меряет нижнюю
   границу вклада роликов» (атрибуция органики дырявая по природе).

## Solution

Сквозная нить «ролик → переход → заказ» из четырёх частей:

1. **Публикация с аккаунтом.** В системе появляется реестр своих аккаунтов
   (5 слотов, как `creator_slots`). Кнопка «Опубликован» в очереди съёмки
   пульта пишет ролик в CF Published Reels с аккаунтом. Продюсер размечает
   публикацию за ~30 секунд, ничего на каждый ролик руками считать не надо.
2. **Сборщик `cf collect metrika`.** Ежедневно по таймеру забирает из
   Metrika API: дневные переходы по UTM (аккаунт × метка ролика), месячные
   уникальные посетители по аккаунтам (биллинговая цифра) и покупки
   e-commerce с суммой и UTM-атрибуцией (кандидаты в заказы). Пишет в две
   новые вкладки Sheets: «CF UTM Traffic» и «CF Orders».
3. **Реестр заказов со статусами.** Кандидаты из Метрики попадают в реестр;
   владелец в пульте подтверждает «оплачен, не возвращён» / «возврат» /
   «не наш». Ручное добавление заказа формой — на случай, когда e-commerce
   событие не дошло. Подтверждённая выручка — единственное, с чего считается
   процент с продаж.
4. **Страница «Деньги» в пульте.** Переходы по аккаунтам за месяц, заказы,
   расчётный лист продюсера (уники × ставка за переход + процент ×
   подтверждённая выручка, с холдом), генератор UTM-ссылок для bio, по-роликовая таблица
   (точное/оценка), markdown-экспорт листа. Те же по-роликовые сигналы
   уходят в eval-датасет — формулы начинают судиться по переходам и выручке.

## User Stories

1. Как владелец, я хочу видеть уникальные переходы по UTM из роликов за
   месяц по каждому аккаунту, чтобы платить продюсеру по цифре, которую
   не оспорить.
2. Как продюсер, я хочу видеть ту же цифру переходов в том же пульте, чтобы
   быть уверенным, что мне платят по тем же данным, которые вижу я.
3. Как владелец, я хочу реестр заказов с UTM-атрибуцией и статусами, чтобы
   процент с продаж платился только с оплаченных и не возвращённых заказов.
4. Как владелец, я хочу подтверждать/отклонять заказ одним кликом в пульте,
   чтобы «подтверждённая продажа» не требовала таблиц руками.
5. Как владелец, я хочу вносить заказ вручную, если e-commerce событие не
   дошло до Метрики, чтобы продюсер не терял свой процент с продаж из-за техники.
6. Как продюсер, я хочу расчётный лист за месяц (переходы × ставка + %
   с продаж, с холдом), чтобы понимать свой доход до копейки.
7. Как владелец, я хочу markdown-экспорт расчётного листа, чтобы отправить
   его продюсеру/в оффер без скриншотов.
8. Как продюсер, я хочу готовые UTM-ссылки по каждому аккаунту (и
   опционально по ролику), чтобы соблюдать UTM-дисциплину копипастой, а не
   ручной сборкой параметров.
9. Как продюсер, я хочу отмечать публикацию ролика в очереди съёмки
   (URL + аккаунт), чтобы связка бриф → ролик → аккаунт появлялась в
   момент публикации.
10. Как владелец, я хочу по-роликовую разбивку переходов (точную по метке,
    оценочную по модели), чтобы видеть, какие ролики реально ведут на сайт.
11. Как eval-агент, я хочу переходы и выручку в строках eval-датасета,
    чтобы судить формулы и промпты по деньгам, а не только по охвату.
12. Как владелец, я хочу видеть в каждом отчёте сноску «это нижняя граница
    вклада роликов», чтобы цифры не читались как «канал слабее, чем есть».
13. Как владелец, я хочу, чтобы сбор шёл сам по таймеру и логировался в
    Run Log, чтобы контур не требовал ежедневных ручных действий.
14. Как владелец, я хочу, чтобы при пустом реестре аккаунтов пульт громко
    объяснял, чего не хватает, а не молча прятал функции.
15. Как владелец, я хочу пилотные ставки в конфиге (ставка за переход / процент
    с продаж / холд), чтобы
    пересмотр ставок через 2 месяца был правкой одной строки, а не кода.
16. Как владелец, я хочу, чтобы возможный переезд с КИТа на свой сайт не
    ломал контур (источник заказов — адаптер), чтобы решение о сайте
    принималось по бизнесу, а не по цене переделки.

## Implementation Decisions

**UTM-конвенция** (генерирует контур, расставляет продюсер):
- `utm_source` = платформа (`tiktok` | `instagram`);
- `utm_medium` = `cf-organic` (константа завода, фильтр всех запросов);
- `utm_campaign` = слаг аккаунта из реестра;
- `utm_content` = `reel_id` (опционально, когда ссылка ставится под ролик).
Базовый URL сайта — в конфиге (`site.base_url`, сейчас `https://jelapeche.com`).

**Реестр аккаунтов** — верхнеуровневый ключ `accounts` в `cf.config.json`:
список `{slug, platform, handle, active}`. Слаг — значение поля, как
`creator_slots`: смена хэндла = правка одной строки. Читают его кнопка
публикации (валидация), генератор ссылок и сборщик (маппинг
`utm_campaign → аккаунт`). Пустой реестр — функции публикации/денег
показывают причину, не прячутся молча (образец — пустые `creator_slots`).

**Публикация.** `mark_published` получает параметр `account` (валидация по
реестру), пишет новую колонку `account` в CF Published Reels; колонка — в
`EXPECTED_COLUMNS` (health-чек дрейфа). CLI `cf mark-published` получает
`--account`. Существующая форма «Опубликован» с карточки брифа дублируется в
очередь съёмки, обе получают select аккаунта. Существующий POST-роут
расширяется, редирект возвращает туда, откуда пришли.

**Сборщик `cf collect metrika`** — по образцу performance (без реестра
источников, без ingestion-гейта): свой `MetrikaClient` (httpx, инъекция
клиента как шов для тестов, `with_retry`, OAuth-токен из файла
`~/.cf/secrets/metrika-token.txt`, счётчик — `metrika.counter_id` в конфиге).
Три запроса Reporting API за прогон:
1. дневные визиты/уники: date × utm_campaign × utm_content (фильтр по
   `utm_medium=cf-organic`) → upsert в CF UTM Traffic по ключу
   `utm_id = date+campaign+content`;
2. месячные уникальные посетители по utm_campaign (с 1-го числа по сегодня;
   отдельно за прошлый месяц в первые дни нового — окно дозаписи) → upsert
   строк гранулярности `month × account` (биллинговая цифра, никогда не
   вычисляется суммой дневных);
3. e-commerce покупки: purchase id, дата, выручка, UTM last-click → upsert в
   CF Orders со `status=candidate` (существующие строки не затираются —
   merge сохраняет решённые статусы).
Dry-run пишет JSONL в `agent-runtime/collect/`, Run Log — `collect-metrika`,
Telegram-алерт при failed — всё по существующему тракту CLI. Отсутствие
токена/счётчика — честный `insufficient_data` с перечнем недостающего.

**Реестр заказов.** Вкладка CF Orders: `order_id`, `source`
(`metrika_ecommerce` | `manual`; позже `kit_api`/`site_webhook`), `order_date`,
`revenue`, `utm_source/campaign/content`, `account` (резолв по campaign),
`reel_id` (из utm_content, если был), `status`
(`candidate`/`confirmed`/`returned`/`rejected`), `status_changed_at`,
`decided_by`, `notes`. Статусы меняет только человек в пульте (POST с CSRF,
Run Log `dashboard-order`); сборщик статусы не трогает. Атрибуция заказа —
ласт-клик Метрики; своей модели атрибуции заказов не изобретаем.

**Страница «Деньги»** (`/money`, вкладка в nav): секции «Расчётный лист»
(выбор месяца), «Переходы по аккаунтам», «Заказы» (кнопки статусов + форма
ручного заказа), «Ссылки для bio» (генератор по реестру + конструктор
per-reel ссылки), «По роликам» (точные/оценка, бейдж «оценка»).
Контекст — чистые функции в отдельном модуле (по контракту `queues.py`:
без часов и побочек, время аргументом). Экспорт `?format=md` — по образцу
markdown-выгрузки очереди съёмки. Сноска о нижней границе — в шаблоне листа
и в экспорте, всегда.

**Расчётный лист** (правила из оффера, зашитые в чистую функцию):
`уники_месяца_по_аккаунтам × payout.per_transition_rub` +
`подтверждённая_выручка_заказов_месяца × payout.sales_percent`.
Холд: заказ входит в лист, только если с даты заказа прошло ≥
`payout.hold_days` на момент формирования; молодые заказы показываются
строкой «в холде, войдёт в следующий лист». Опциональный
`payout.monthly_fix_rub` (месяц → сумма) добавляет строку фикса стройки.
Ставки — пилотные, живут в `cf.config.json → payout`
(`per_transition_rub`, `sales_percent`, `hold_days`; в `cf.config.example.json`
стоят условные значения-примеры, реальные пилотные ставки в витрине не
публикуются).

**По-роликовая оценка** (чистый модуль атрибуции): точные клики — строки
CF UTM Traffic с `utm_content`; остаток дневных визитов аккаунта
распределяется по роликам этого аккаунта, опубликованным в последние 14
дней, пропорционально их последним известным просмотрам из CF Performance
(нет просмотров — равными долями). Каждое оценочное число помечено
`estimated`. Оценка не хранится в Sheets — пересчитывается на лету
(страница, eval-выгрузка).

**Eval.** `build_eval_dataset` получает аргументы `utm=None, orders=None`
(по образцу `reels=None`); строки обогащаются `clicks_exact`,
`clicks_estimated`, `orders`, `revenue`; агрегаты по версиям промпта и
когортам формул расширяются теми же полями; предупреждение в `warnings`,
когда вкладки пусты. Оба вызова датасета (eval-prep и `_measured_rows`)
прокидывают новые вкладки. Промпт eval-агента правится НЕ напрямую:
черновик в `proposals/` + аппликатор `cf apply-agent-edit` (правило №3).

**Деплой и ротация.** systemd-пара `cf-collect-metrika.{service,timer}`
(ежедневно 08:20, между raw 08:00 и performance 08:40), строка в подсказке
`install.sh`. CF UTM Traffic (дневные строки растут) — в `ARCHIVE_TABS` по
дате; CF Orders не ротируется никогда (источник истины по деньгам).
Backup/restore покрывают обе вкладки автоматически (обход `tabs`).

**PLACEHOLDER — заполняет владелец при приёмке** (имена, не значения):
`metrika.counter_id`; файл `~/.cf/secrets/metrika-token.txt`; хэндлы в
`accounts`; проверка в настройках КИТа, что счётчик Метрики подключён и
e-commerce события включены (галка, не код).

## Testing Decisions

- Тестируется внешнее поведение: строки, попавшие в FakeSheets; JSONL
  dry-run; HTTP-статусы и редиректы роутов; тексты markdown-экспорта.
  Реализация (какие именно запросы к Метрике внутри клиента) — за швом
  фейк-клиента.
- Чистые функции (расчётный лист, атрибуция, нормализация строк Метрики) —
  плотные юнит-тесты с граничными случаями (пустой месяц, заказ в холде,
  возврат, ролик без просмотров, неизвестный utm_campaign).
- Сборщик — с инъекцией фейкового MetrikaClient (образец — `StubClient` в
  `tests/test_cli_collect.py`); сеть в тестах заблокирована conftest'ом.
- Роуты — TestClient + FakeSheets с явными заголовками (образец —
  `tests/test_dashboard_routes.py`, включая CSRF-заголовки BROWSER).
- Инварианты конфига (вкладки, алиасы, ставки payout) — дополнение
  `tests/test_config_invariants.py`.
- Прогон: `.venv/bin/python -m pytest -q`; полный сьют один раз в конце.

## Out of Scope

- Автоскрейп своих аккаунтов (авто-mark-published) — следующий этап.
- Редиректор-домен коротких ссылок — пока некуда ставить per-video ссылки.
- Прямая интеграция с API КИТа (публичного API нет) и CRM-коннекторы —
  реестр заказов готов принять их новым `source`.
- Переезд на самописный сайт и вебхук заказов с него.
- Изменение схемы/ставок оплаты (ставки — конфиг, пересмотр — вне кода).
- own_performance формул по заказам, demo-seed для новых вкладок,
  Telegram-уведомления о заказах, разделение вкладов формула/криэйтор.

## Further Notes

- Атрибуция органики дырявая по природе: часть зрителей купит через поиск
  без метки. Контур меряет НИЖНЮЮ границу вклада — сноска обязательна во
  всех отчётах (решение из брифа, проговорено при выборе схемы оплаты).
- Объём 70 роликов/нед: ни одного нового ручного действия «на каждый
  ролик», кроме уже существующей публикации (30 сек в очереди съёмки).
- Первые 2 месяца ставки пилотные — контур одновременно калибровочный
  инструмент схемы найма.
- Ключ связей завода дорастает до денег:
  `source_url → pattern → formula → brief → reel → performance → clicks/orders`.
