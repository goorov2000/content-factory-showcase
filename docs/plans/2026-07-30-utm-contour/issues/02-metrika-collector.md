# 02 — Сборщик cf collect metrika

**What to build:** Новый сборщик забирает из Яндекс.Метрики трафик по UTM и
пишет его в новую вкладку «CF UTM Traffic». `cf collect metrika` (и dry-run с
JSONL в `agent-runtime/collect/`) делает два класса запросов Reporting API с
фильтром `utm_medium=cf-organic`: (1) дневные визиты/уники в разрезе
`date × utm_campaign × utm_content` — upsert по `utm_id`; (2) уникальные
посетители месяца по `utm_campaign` (месяц-к-дате; в первые 3 дня месяца —
дозапись прошлого месяца) — upsert строк `month × account`; биллинговая
цифра никогда не считается суммой дневных уников. Клиент — свой
`MetrikaClient` с инъекцией http-клиента (шов для тестов), `with_retry`,
OAuth-токен из `~/.cf/secrets/metrika-token.txt`, `counter_id` из блока
`metrika` конфига. Прогон логируется в Run Log как `collect-metrika` (подпись
в лентах дашборда — человеческая). Нет токена или counter_id — честный
`insufficient_data` с перечнем недостающего, не падение.

**Blocked by:** 01 (реестр аккаунтов: маппинг `utm_campaign → слаг`).

**Status:** done

- [x] `cf collect metrika --dry-run` без токена печатает `insufficient_data`
  и перечень недостающего; с фейковым клиентом в тестах — пишет JSONL и не
  трогает Sheets.
- [x] Боевой прогон (в тестах — FakeSheets) создаёт вкладку при отсутствии
  (`ensure_tab`), upsert'ит дневные и месячные строки, не плодя дубли при
  повторном прогоне за тот же день.
- [x] Строки несут `account` (резолв слага по utm_campaign; неизвестный
  campaign — строка сохраняется с пустым account и попадает в счётчик
  предупреждений сводки).
- [x] Run Log получает строку `collect-metrika` на каждом исходе
  (success / insufficient_data / failed), exit-коды как у остальных стадий.
- [x] Тесты: нормализация ответа Метрики, месячный upsert (2 прогона в один
  день → 1 строка), dry-run, insufficient_data, retry-поведение клиента на
  429. Полный сьют зелёный.

## Комментарии

2026-07-30 — сделано, +20 тестов (metrika 15: нормализация 2, collect 7,
клиент 4, отказы/метка 2; CLI 4; инвариант конфига 1), полный сьют 1762 passed.
Отклонения от буквы спеки: (1) пустой отчёт Метрики — `success` с пометкой
«переходов не найдено», не `insufficient_data`: ноль переходов — честный замер,
иначе Telegram слал бы алерт каждый день до первого клика; insufficient_data
оставлен за отсутствием counter_id/токена. (2) Окно перезабора дневных строк —
константа `DAILY_LOOKBACK_DAYS = 7` (спека окно не фиксировала; данные Метрики
дозревают, upsert перезаписывает снапшот). (3) Строки cf-organic без
utm_campaign пропускаются — вне конвенции, ключ utm_id не построить.
(4) e-commerce покупки (третий запрос спеки) — скоуп тикета 03, здесь два
класса запросов по тексту тикета. Даты запросов — UTC; имена
dimensions/metrics — константами в шапке `src/cf/collect/metrika.py`, правятся
в одном месте на приёмке с живым токеном. Инжектированный в тестах client
пропускает проверку конфига осознанно: шов несёт counter сам.
