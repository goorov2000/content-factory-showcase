# Proposal: ревьюер логирует прогон сам — правило №6 в промпт агента

## Current version

У `prompts/agents/brief-reviewer.md` шага `log-run` НЕТ ВООБЩЕ. Файл — 51 строка,
четыре секции: `# Brief Reviewer` (1), `## Проверки (по строгости)` (5),
`## Вердикты` (28), `## Правила` (38). Ни секции «Выход», ни «Длительность
прогона», ни слова `log-run`, ни слова `--started-at`:

```
$ grep -c log-run prompts/agents/brief-reviewer.md     -> 0
$ grep -c started-at prompts/agents/brief-reviewer.md  -> 0
$ grep -c log-run prompts/agents/brief-generator.md    -> 6
```

Контракт правила №6 у ревьюера живёт целиком в слэш-команде
`.claude/commands/cf-review-brief.md`, шагом 7 из 8 — ПОСЛЕ длинного пер-брифного
цикла шага 6 (снапшот → валидация → формула → проверки → review-JSON → auto-approve /
set-review на каждый бриф очереди):

```
46: 7. Залогируй: `.venv/bin/python -m cf log-run --agent brief-reviewer --status success
47:    --input "<brief_id или pending:N>" --outputs <review-файлы>`.
48: 8. Покажи оператору вердикты и причины по каждому брифу.
49: Перед началом работы запомни время старта (`date -u +%Y-%m-%dT%H:%M:%S+00:00`) и передай его в log-run флагом `--started-at <запомненное время>` — иначе длительность прогона в CF Run Log будет нулевой.
```

Три дефекта в этих четырёх строках:
1. статус захардкожен `--status success` — исходов у прогона четыре, три из них
   нечем выразить, и «разобрал половину очереди» логировать нечем;
2. нет барьера «ход не завершать до этой строки» — шаг 7 отделён от результата
   работы всем циклом шага 6 и в длинном прогоне теряется;
3. директива про время старта стоит ПОСЛЕ шага 8 — последней строкой файла, хотя
   предписывает действие ПЕРЕД первым шагом.

Холостой путь у ревьюера закрыт (`.claude/commands/cf-review-brief.md:9-12`,
proposal 2026-07-24-log-run-on-idle-paths) — а рабочий остался незакрытым.

## Proposed changes

**1. `prompts/agents/brief-reviewer.md` — добавить в конец файла, после секции
`## Правила`, две новые секции. Дословный текст:**

```markdown
## Лог прогона (правило №6)
Строка в CF Run Log — ПОСЛЕДНЕЕ действие по работе, но идёт ДО сводки оператору.
Ход не завершается, пока строки нет: сводка без строки — это прогон, которого для
системы не было.

`.venv/bin/python -m cf log-run --agent brief-reviewer --status <статус>
 --input "<brief_id | pending:N>" --outputs <review-файлы>
 --started-at <запомненное время старта>`

Статус — по факту исхода, а не по настроению. Исходов четыре, и строка обязательна
в каждом:
- **success** — очередь разобрана до конца: у каждого взятого брифа есть вердикт и
  он проведён в таблицу (`cf auto-approve` при recommend, `cf set-review` при
  revise/reject);
- **skipped** — pending-брифов не было: `--input "нет pending-брифов"` (тот же
  случай, что шагом 1 команды /cf-review-brief);
- **insufficient_data** — разобрана ЧАСТЬ очереди: кончился контекст, не открылись
  raw-строки для проверки 4, упала команда на середине. Счётчик остатка — в
  `--errors "разобрано K из N: <что осталось и почему>"`. Правило №2 требует
  честного статуса, правило №6 — строки: недоделанный прогон логируется ТОЖЕ,
  молча выйти нельзя;
- **failed** — прогон упал: `--errors "<ошибка>"`.

**Уходить в фон запрещено.** Не отвечай «вернусь с финалом по уведомлению» и не
откладывай лог «на потом»: дашборд зовёт ревью headless (`claude -p`), где
возврата не существует — процесс кончается вместе с ходом, и всё, что осталось
после сводки, не выполняется никогда. Инцидент 2026-07-26 18:46: 12 ревью-файлов
записаны, брифы проведены через auto-approve, лог отложен — строки brief-reviewer
в Run Log нет, звено дашборда легло как insufficient_data с проблемой «ревью
брифов: агент brief-reviewer не оставил след в Run Log (правило №6) — прогон
холостой или лог пропущен». Работы больше, чем влезает в один ход → закрой ход
логом `insufficient_data` и перечисли остаток в `--errors`.

## Длительность прогона
Перед первым действием запомни время старта:
`date -u +%Y-%m-%dT%H:%M:%S+00:00`
и передай его КАЖДОМУ вызову `cf log-run` флагом `--started-at <запомненное время>`.
Без него `started_at` подставляется моментом записи строки, длительность в CF Run Log
выходит нулевой, а медианы прогонов врут (proposal 2026-07-25-log-run-started-at).
```

Секция «Длительность прогона» скопирована из `prompts/agents/brief-generator.md:74-79`
СЛОВО В СЛОВО и намеренно: proposal 2026-07-25-log-run-started-at требует «единую
формулировку для всех агентов», и свой вариант текста здесь был бы регрессом.

  `find agent-runtime/reviews -name '*-review.json' -newermt '2026-07-26 18:30'

## Confidence

high — дефект воспроизведён на боевых данных (12 файлов ревью против нуля строк в
Run Log), корень зафиксирован дословной цитатой самого агента, а лечение
симметрично уже работающему образцу: у `brief-generator` те же четыре исхода
описаны в промпте агента, и пропусков у него нет. Правка чисто текстовая, кода не
касается, страж и его 53 теста остаются как есть.

## Risks

1. **Дублирование контракта в двух файлах.** Инструкция про лог окажется и в
   промпте агента, и в слэш-команде. Это осознанно: слэш-команда задаёт порядок
   шагов, промпт — разбор статусов; при расхождении источник истины —
   `prompts/agents/brief-reviewer.md`, о чём шаг 7 говорит явной ссылкой на раздел.
   Альтернатива (оставить только в команде) — ровно то состояние, которое дало
   инцидент.
2. **Строк в Run Log станет больше** за счёт `insufficient_data` на недоделанных
   прогонах. Это цель, а не издержка: сейчас недоделанный прогон неотличим от
   несостоявшегося. Побочно вырастет доля не-`success` строк у ревьюера — при
   чтении `cf status` это надо трактовать как «стало видно», а не «стало хуже».
3. **Агент может проставить статус формально** (`success` на половине очереди).
   Машинной проверки соответствия статуса объёму работы нет; страж считает только
   наличие строки. Смягчение — счётчик «разобрано K из N» в `--errors` сверяется с
   числом review-файлов прогона при разборе полётов.
4. **Правка не устраняет причину класса «ход кончился раньше работы»** для других
   агентов. Если тот же уход в фон повторится у niche-classifier или eval-agent,
   лечить придётся так же — точечно. Общего механизма «лог при завершении хода» в
   системе нет и этим proposal не вводится.
