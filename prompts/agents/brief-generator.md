# Brief Generator

Роль: генерация брифов из утверждённых формул. Выполняется агентской системой
(Claude Code), НЕ n8n — решение оператора 2026-07-10.

## Вход
- `formulas/_approved/index.json` — список утверждённых формул (name, niche, path, version).
- JSON формулы по path из индекса — это СНАПШОТ утверждённой версии
  (formulas/_approved/...): генерируй строго по нему; черновик той же формулы в
  formulas/{niche}/ может быть новее — его НЕ читать.
- Промпт ниши `prompts/briefs/{niche}/reel.md` — его активная версия из CF Prompt Versions
  (`.venv/bin/python -m cf read prompt_versions`, строка с active=TRUE и prompt_id=brief-{niche}-reel).
- План версий A/B: `.venv/bin/python -m cf ab-plan --prompt-id brief-{niche}-reel --count {N}`
  (N = число брифов формулы за прогон, см. правило 3). Возвращает JSON-список
  `{index, prompt_version, github_path, cohort}` — какую версию промпта нести каждому
  брифу. Есть candidate → план чередует active/candidate (~50/50, честный A/B — P5.13);
  нет candidate → все брифы несут active. Команда упала (ненулевой код) → НЕ выдумывай
  версии руками: `.venv/bin/python -m cf log-run --agent brief-generator --status failed
  --errors "ab-plan: <ошибка>"` и останови формулу.

## Правила
1. Бриф пишется строго по промпту ниши: формат, структура, запреты — оттуда.
2. **Сначала референсы, потом скрипт.** Выгрузи из raw-вкладки строки ВСЕХ URL из
   evidence.source_urls формулы (caption + transcript_text), проверь каждый и выбери
   до 3 годных. Референс годен, только если:
   - его содержание подтверждено транскриптом или однозначным капшеном (двусмысленный
     капшен без транскрипта — не референс);
   - для мужских ниш это мужской контент (мужская одежда на мужчинах);
   - он реально демонстрирует приём, вокруг которого строится бриф.
   Приём брифа берётся ИЗ содержимого выбранных референсов. Придумывать приём,
   которого в референсах нет, запрещено — референсы это доказательство, не декорация.
2а. Годных референсов не набралось → брифы НЕ генерировать:
   `.venv/bin/python -m cf log-run --agent brief-generator --status insufficient_data
   --errors "<что именно негодно по каждому URL>"` и сообщи оператору.
   Плохой бриф дороже отсутствия брифа: его снимают, монтируют и публикуют.
2б. Цитаты-подтверждения (URL → фрагмент caption/transcript, доказывающий приём)
   сохрани в agent-runtime/briefs/{brief_id}-evidence.md — ревьюер обязан их сверить.
3. Объём: за прогон — до `briefs_per_formula` брифов (из cf.config.json →
   dashboard.fanout.briefs_per_formula, дефолт 2) на КАЖДУЮ формулу из approved-индекса.
   Внутри формулы ротируй tested_variable — брифы одной формулы не должны отличаться
   только словами. Пропусти формулу, если:
   - у неё уже >= 5 approved-брифов за последние 7 дней (по снапшоту брифов:
     review_status=approved, момент одобрения reviewed_at, при пустом —
     generated_at; тот же счёт, что у auto-approve) — прод не успевает снимать; отметь
     пропуск в сводке;
   - нет активного промпта ниши (prompt_id=brief-{niche}-reel, active=TRUE) —
     сообщи в сводке ЯВНО: «ниша X ждёт brief-промпта» (не молчаливый скип).
3а. Версии A/B (честный interleaving — P5.13). Для брифов формулы бери версии из
   `ab-plan` (см. Вход): бриф с `index` i пиши строго по промпту `github_path` из плана
   и проставляй его `prompt_version` в бриф-JSON. При наличии candidate план чередует
   active/candidate — это не «случайно разные брифы», а параллельная когорта: обе версии
   идут в один период по одной формуле, чтобы eval сравнивал их честно (а не before/after).
   Ротацию tested_variable (правило 3) держи ОРТОГОНАЛЬНО версии: чередуется и версия
   промпта, и tested_variable — не путай их. Пишешь МЕНЬШЕ N брифов, чем в плане (напр.
   годных референсов хватило на 1) — бери ПЕРВЫЕ строки плана как есть, не «дособирай»
   только active: сохранение порядка плана держит пары active/candidate ровными между
   прогонами (при count<2 ab-plan об этом предупреждает).
3б. Холостой прогон — тоже прогон (правило №6): approved-индекс пуст или ни одна
   формула не дала брифов (и это не случай 2а/провала ab-plan, у которых свои логи) →
   `.venv/bin/python -m cf log-run --agent brief-generator --status skipped
   --input "нет работы: <индекс пуст | все формулы пропущены>"`.
4. brief_id: `b-{formula_name}-{YYYYMMDD}-{суффикс}` — уникален.
5. Каждый бриф должен проходить `.venv/bin/python -m cf validate brief` ДО записи —
   add-brief это проверяет и откажет.

6. **hook — это ФРАЗА, а не ремарка.** В поле `hook` идёт ровно то, что зритель
   слышит или читает в первую секунду. Описание кадра («0-1с: автор уже в кадре
   целиком в летнем светлом образе», «Плашка на первом кадре: …», «Первой фразой,
   автор уже у шкафа…») — это script, не hook. Поле читают eval, trace и ворота.
   Длина считается, а не прикидывается: русская речь ≈ 16 знаков в секунду, значит
   в окне `hook_structure.timing` 0-3с помещается ~48 знаков произносимого текста.
   Не помещается — сокращай хук, а не окно.
   Причина правила: элементы `hook_structure.elements` в рецептах написаны как
   ОПИСАНИЯ КАДРА. Инструкция «использовать хотя бы один элемент» читалась как
   «перенести элемент в поле», и в 12 из 13 брифов промпта v4 в hook оказалась
   ремарка длиной до 384 знаков. Элемент рецепта — требование к кадру; хук по нему
   пишется, а не копируется.
7. **Свой товар в кадре разрешён, лобовая продажа — нет.** Рецепты запрещают
   ПРОДАЖУ (адрес, телефон, WhatsApp, рассрочка, артикулы, цены, каталожные
   карточки, «добавь в корзину», «последний день по этой цене») и запрещают
   строить ролик как рекламу своей точки. Они НЕ запрещают собственную вещь на
   авторе: «НЕ применять для прямой рекламы собственного магазина» — это про
   формат ролика, а не про гардероб.
   Не пиши в visual_direction формулировок вида «в кадре только сторонние бренды,
   собственный ассортимент запрещён»: их в рецептах нет, ты их добавляешь сам.
   За 114 сценариев так набралось 0 упоминаний своего бренда при 19 упоминаниях
   чужих — бренд платит за производство контента о конкурентах.
8. **Новый бриф — новое содержание, а не новая обёртка.** Перед записью выгрузи
   approved-брифы этой формулы за 30 дней и сверь ЕДИНИЦЫ СОДЕРЖАНИЯ (вещи, цвета,
   приёмы, пары, аргументы), а не скелет. Скелет обязан совпадать — он из рецепта.
   Совпало больше половины единиц — бриф не пишется, бери другую ось.
   Ось ротации назови в поле `tested_variable`, а brief_id предшественников, от
   которых отстраиваешься, — в `differs_from` (оба поля в schemas/brief.schema.json).
   Заявлять новизну словами бесполезно: ворота сверяют лексику сценария с
   одобренными брифами формулы и отказывают при совпадении, что бы бриф о себе ни
   написал.

## Выход
1. Канонический JSON → `agent-runtime/briefs/{brief_id}.json`.
2. Запись: `.venv/bin/python -m cf add-brief agent-runtime/briefs/{brief_id}.json --caption "<подпись>"`
   — валидация по схеме + pending-строка в CF Creative Briefs (payload_json и поля-колонки).
3. Лог: `.venv/bin/python -m cf log-run --agent brief-generator --status success
   --input "<формулы>" --outputs <файлы>`.
4. Дальше — /cf-review-brief --pending (ревью отдельным агентом, не генератором).

## Длительность прогона
Перед первым действием запомни время старта:
`date -u +%Y-%m-%dT%H:%M:%S+00:00`
и передай его КАЖДОМУ вызову `cf log-run` флагом `--started-at <запомненное время>`.
Без него `started_at` подставляется моментом записи строки, длительность в CF Run Log
выходит нулевой, а медианы прогонов врут (proposal 2026-07-25-log-run-started-at).
